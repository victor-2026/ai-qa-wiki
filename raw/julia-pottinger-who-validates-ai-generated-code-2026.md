# Who Is Accountable for AI-Generated Code?

**Source:** https://juliapottinger.com/who-validates-ai-generated-code/?utm_source=softwaretestingweekly&utm_medium=email&utm_campaign=issue-325 (redirects to https://juliapottinger.com/who-validates-ai-generated-code/ → Who Is Accountable for AI-Generated Code?)
**Author:** Julia Pottinger (QA, JPott Studios)
**Date:** August 25, 2026, 10 min read

Most days now I build software with AI agents, and I am the one who signs off on what they write. On my own game, the agent produces a chunk of code, I accept it, and if it ships broken there is nobody to point at but me. That clarity is a luxury of working alone. On a team it gets murky fast.

Here is the version I watch for. A change lands in production and breaks something. Someone pulls up the pull request to find out who to talk to. The code was generated by an agent, accepted with a quick glance, approved by a reviewer who was moving fast, and merged. Every person in that chain assumed someone else had really checked it. Nobody had. The gap there is not in the testing. It is in ownership.

Agent Generates → Developer Accepts (quick glance, assumes agent got it right) → Reviewer Approves (moving fast, assumes author checked) → Production Breaks (nobody can answer). Authorship moved to tool, accountability fell out.

Generating code is not the same as owning it. When I write function by hand, authorship and accountability arrive together. I understand because I built line by line. When agent writes, authorship moves to tool, reading is optional, author is gone at failure time. So accountability has nowhere to land unless person deliberately picks it up.

> A tool can produce code. A tool cannot be accountable for it.

Why "the developers will catch it" is not an ownership model. Diffusion of responsibility — more people who could act, less any single person feels they must. Author assumes agent got it right, reviewer assumes author checked. Green review can mean "I read and stand behind it" vs "looked fine and tests passed" — thumbs-up doesn't distinguish. If approval rested on passing suite, ownership rested on tests, and AI-written tests tend to confirm what code already does.

Name an accountable owner for every AI-assisted change. RACI: exactly one Accountable per change, never tool/committee. Table: Developer (prompter) Accountable for understand what change does, confirm solved right problem, own rollback; QA Accountable for verify tests would fail on real bug, sign off risk acceptable; Tech lead Accountable for policy. Agent appears nowhere — tool cannot hold letter.

The "can I sign off" test (5 questions):
1. Can I explain what change does in one honest paragraph without re-reading agent summary?
2. Do I know what problem it meant to solve, and why this solves it not plausible neighbour?
3. If breaks at 2am, am I person called, could I start debugging?
4. Is there at least one test here that would actually go red if behaviour were wrong?
5. If teammate asked "are you sure," would answer be evidence or shrug? Last carries most weight.

Record sign-off where change lives. Put in artifact, not head. Pull request block:
```
## AI-assisted change
- Generated with: <agent/tool>
- Accountable owner: @name (understands, owns rollback)
- What it does (my own words): ...
- Risk if wrong, who it affects: ...
- Evidence it works: <link to test that would fail on real bug>
- QA sign-off (risk acceptable): @name
- If unverifiable before release: monitor + owner + rollback plan
```
Makes owner write in own words (cheapest understand test), separates developer accountability from QA sign-off, leaves record for postmortem.

Ownership has to scale to volume, not line. Honest objection: can't keep up if 10× code. Scale by risk, not line: Low risk (copy, styling, internal tooling) → developer owner only, no second sign-off; Medium (new feature path, changed query, user-facing) → named developer owner + real review (reviewer can pass can-I-sign-off test too); High (auth, payments, data integrity) → named developer owner AND explicit QA sign-off recorded before merge. Use GitHub CODEOWNERS to route high-risk directories to owners.

Where this leaves you: AI changed who writes code, not who answers for it. Judgment about whether change is right to ship is part it cannot hold. Teams that let authorship move to tool and forgot to hand accountability to person get into trouble. Teams that keep ownership explicit: one accountable name per change, sign-off sized to risk, record where change lives.

If you make one move this week, add AI-assisted block above to PR template and require named accountable owner on anything touching auth, payments, or data.
