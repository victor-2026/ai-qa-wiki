## Проблема: почему DS/ML тестирование отличается

DS-модели принципиально отличаются от детерминированного кода:

| Детерминированный код | DS/ML модель |
|-----------------------|-------------|
| Один и тот же input = один output | Один input может давать разные output (вероятностно) |
| Можно написать assert(expected, actual) | Нужны метрики качества (AUC, precision, recall) |
| Баг = ошибка в коде | «Баг» = деградация качества модели |
| Фиксится изменением кода | Фиксится переобучением, новыми данными, tuning |

## 4-уровневая модель тестирования DS/ML

### Level 1: Property-Based Testing (PBT)

Проверяем **инварианты** — свойства, которые должны выполняться всегда, независимо от вероятностной природы модели.

**Примеры инвариантов:**
- Цена продвижения >= 0 (неотрицательна)
- Сумма вероятностей всех исходов = 1
- Ранжирование не меняется при одинаковых параметрах
- AUC не падает ниже порога после retrain

**Инструменты:**
- fast-check (JS/TS)
- testing/quick (Go)
- Hypothesis (Python)
- property-based тесты в любом языке

### Level 2: A/B Эксперименты с Statistical Significance Gate

Перед rollout модели — экспериментальная валидация:

| Этап | Что делаем | Критерий успеха |
|------|-----------|-----------------|
| Power analysis | Определяем минимальный размер выборки | 95% confidence, 80% power |
| A/B test | Контрольная группа (старая модель) vs экспериментальная | Статистически значимое улучшение |
| Guardrail метрики | Мониторинг побочных эффектов | Revenue не падает, churn не растёт |
| Временные рамки | Минимум 1 неделя (учёт day-of-week) | Full cycle |

**Роль QA:** Проверить, что эксперимент корректно настроен, метрики записаны, guardrails активны.

### Level 3: Drift Detection

Модель в production деградирует со временем. Нужен мониторинг:

| Тип дрифта | Что происходит | Как обнаружить |
|------------|---------------|----------------|
| **Data drift** | Распределение входных признаков меняется | Сравнение распределений (KS-test, PSI) |
| **Concept drift** | Связь признак→таргет меняется | Мониторинг метрик качества в реальном времени |
| **Upstream drift** | Данные от источника изменились | Валидация схемы данных |

**Автоматизация:** Алерт при превышении порога → откат на предыдущую версию модели → анализ причин.

### Level 4: Golden Dataset

Эталонный набор данных для регрессионного тестирования:

- Фиксированный набор размеченных примеров
- Прогоняется при каждом изменении модели
- Метрики сравниваются с baseline
- Если метрики упали — модель не катится

**Пример:** 10,000 объявлений с известной ценой продвижения. После retrain проверяем, что MAE (mean absolute error) не выросла более чем на 5%.

## Процесс: роль QA vs роль DS

| Активность | Владелец | Роль QA |
|-----------|----------|---------|
| Разработка модели | DS-инженер | — |
| PBT на инварианты | QA + DS | Пишет property-based тесты совместно с DS |
| A/B эксперимент | PM + DS | Проверяет корректность эксперимента |
| Drift мониторинг | Инфраструктура + DS | Настраивает алерты, пороги |
| Golden dataset | QA | Собирает, поддерживает, автоматизирует прогон |
| Метрики качества | Test Lead | Дашборд: drift, AUC тренд, ошибки |

## Чеклист для Test Lead

- [ ] Определены инварианты модели (PBT)
- [ ] A/B эксперимент — mandatory gate перед каждой выкаткой
- [ ] Drift detection включён и алертит
- [ ] Golden dataset существует и автоматизирован
- [ ] Метрики качества модели на общем дашборде (Grafana)
- [ ] Процесс задокументирован в TDR

## Резюме для интервью

> «Для DS-моделей использую 4 уровня: 
> 1) Property-based тесты на инварианты модели; 
> 2) A/B эксперименты с statistical significance gate; 
> 3) Drift detection в production; 
> 4) Golden dataset для регрессии. 
> 
> QA строит процесс и метрики, DS-инженеры — domain experts. 
> Ключевой принцип: вероятностные системы не тестируются детерминированными тестами.»
