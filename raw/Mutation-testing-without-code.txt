Этот вид проверки называется мутационным тестированием (англ. Mutation Testing). [1, 2]
Его главная цель — проверить не сам продукт, а качество и надежность ваших автотестов. [1]

Как это работает
Специальный инструмент автоматически вносит мелкие умышленные ошибки (подмены) в рабочий исходный код. Измененная версия программы называется «мутантом».
Происходит запуск ваших существующих тестов на этом измененном коде.
Анализируется результат:
Мутант убит: хотя бы один тест упал. Это отличный результат. Значит, ваши тесты бдительны и сразу замечают поломку логики.
Мутант выжил: все тесты успешно прошли. Это плохой сигнал. Код изменился, но тесты этого не заметили. Значит, в них есть слепые зоны или не хватает проверок (например, граничных значений). 

Примеры подмены кода (операторы мутации)
Замена знаков: > меняется на >=, а + меняется на -.
Изменение логики: if (a && b) превращается в if (a || b).
Подмена возвращаемых значений: return true; заменяется на return false;. [1]
Если вы хотите внедрить этот подход, обратите внимание на популярные фреймворки автоматизации: Stryker Mutator (для JavaScript, .NET и Scala), PITest (для Java) или Mutmut (для Python).

В вашей ситуации запустить классическое мутационное тестирование действительно невозможно. Все стандартные инструменты требуют либо исходный код, либо доступ к процессу сборки (скомпилированному байт-коду) для внедрения мутаций.
Тем не менее, проверить надежность тестов в условиях «черного ящика» можно. Для этого подход разворачивают в обратную сторону: мутируют не код, а входные данные, окружение или запросы.

Альтернативные варианты проверки тестов
Фатчинг / Фаззинг-тестирование (Fuzzing) Вместо изменения кода вы подаете на вход системе хаотичные, невалидные или случайно измененные данные. Если ваши тесты при этом не фиксируют ошибки и продолжают падать или, наоборот, «зеленеть» там, где система должна выдать ошибку 500, значит, тесты не покрывают негативные сценарии.
Мутация API-ответов (Сетевое мутационное тестирование) Если проект доступен как сервис, вы можете перехватывать его ответы (например, через прокси вроде Charles, Fiddler или Mitmproxy) и умышленно портить JSON/XML-пакеты. Так вы проверите, как тесты реагируют на поломку интеграций.
Chaos Engineering (Инженерия хаоса) Мутируйте среду обитания проекта. Специальные утилиты (например, Chaos Mesh) могут имитировать задержки сети, отключать базу данных или забивать оперативную память. Ваши автотесты должны четко отлавливать эти падения инфраструктуры, а не просто зависать.

Полноценный анализ покрытия без кода
Если вам нужно понять, насколько вообще ваши тесты эффективны для этого легаси-проекта, попробуйте оценить покрытие требований:
Составьте карту всех известных функций системы (Black-box спецификация).
Сопоставьте каждый тест с конкретной функцией.
Функции, для которых нет тестов, и будут вашими главными «выжившими мутантами».

В вашей конфигурации (Веб-сайт + API + БД) есть отличные возможности проверять надежность тестов без доступа к исходному коду. Вы можете внедрять «мутации» (ошибки) на стыках этих трех слоев.
Вот 3 практических сценария, как «оживить» мутационное тестирование в вашей ситуации:

1. Мутация данных в БД (Тест на бдительность тестов)
Вместо изменения кода сломайте данные, с которыми этот код работает.
Как сделать вручную или скриптом: Запустите автотесты до шага проверки, поставьте тест на паузу, зайдите в тестовую БД и измените значения. Например, поменяйте статус заказа с New на Archived, обнулите баланс пользователя или запишите спецсимволы в текстовое поле.
Ожидаемый результат: Ваши тесты должны упасть. Если тест успешно завершился и «не заметил», что в базе лежат битые данные — тест не работает и требует переработки.

2. Мутация API через прокси (Эмуляция поломки бэкенда)
Если у вас есть UI-тесты (Selenium, Playwright, Cypress), они ходят к бэкенду через API. Вы можете перехватывать и мутировать эти ответы «на лету».
Инструменты: С工具ами вроде Mitmproxy, Charles Proxy или встроенными возможностями перехвата в Playwright/Cypress.
Примеры мутаций:
Смените статус-код ответа с 200 OK на 500 Internal Server Error.
Удалите из JSON-ответа обязательное поле (например, id или price).
Замените числовое значение строки на null.
Ожидаемый результат: UI-тесты должны упасть, зафиксировав понятную ошибку (например, появление алерта или падение элемента), а не просто зависнуть по таймауту.

3. Фаззинг API (Проверка надежности API-тестов)
Если у вас написаны тесты на само API (например, в Postman), проверьте их устойчивость хаотичными запросами.
Инструменты: Облегченные фаззеры или сканеры уязвимостей (например, OWASP ZAP или Burp Suite Suite).
Суть: Инструмент берет структуру вашего легаси-запроса и начинает подменять параметры на экстремально длинные строки, SQL-инъекции, бинарные файлы.
Ожидаемый результат: Ваши тесты на API должны быть готовы к таким ответам. Они должны падать с ожидаемой ошибкой валидации (400 Bad Request), подтверждая, что тесты умеют отличать корректную работу системы от аварийной.


Если вы хотите автоматизировать этот процесс, проще всего начать с перехвата сетевых запросов в UI-тестах. 

Playwright встроена мощная система перехвата сетевых запросов (Network Interception). Она идеально подходит для имитации «мутаций» бэкенда без изменения самого кода.
Ниже приведены практические примеры, как с помощью функции page.route() проверить, насколько бдительны ваши тесты.

Пример 1. Мутация данных (Изменение JSON-ответа)
Проверим, заметит ли ваш тест, если бэкенд пришлет неверные данные (например, нулевую цену товара).

javascript
import { test, expect } from '@playwright/test';

test('Проверка теста на подмену данных (Цена = 0)', async ({ page }) => {
  // 1. Внедряем МУТАЦИЮ: перехватываем запрос к API и меняем цену на 0
  await page.route('**/api/v1/products/*', async route => {
    const response = await route.fetch();
    const json = await response.json();
    
    // Мутируем поле цены
    json.price = 0; 
    
    // Отправляем измененный JSON обратно в браузер
    await route.fulfill({ response, json });
  });

  // 2. Выполняем обычные шаги теста
  await page.goto('/products/123');

  // 3. Ожидаемый результат: ТЕСТ ДОЛЖЕН УПАСТЬ!
  // Если у вас стоит проверка, что цена отображается корректно, 
  // то этот ассерт завалится. Если тест прошел — значит, он написан плохо.
  await expect(page.locator('.product-price')).toHaveText('$99.99'); 
});

Пример 2. Мутация структуры (Удаление обязательного поля)
Проверим, как UI и тест реагируют, если бэкенд прислал «сломанный» JSON (например, пропало поле со списком товаров).

javascript
test('Проверка теста на отсутствие поля в API', async ({ page }) => {
  await page.route('**/api/v1/dashboard', async route => {
    await route.fulfill({
      status: 200,
      contentType: 'application/json',
      body: JSON.stringify({ 
        user: "Иван", 
        // Поле items умышленно удалено (мутация)
      })
    });
  });

  await page.goto('/dashboard');

  // Тест должен упасть на проверке элементов интерфейса, 
  // а не зависнуть или показать пустую "зеленую" страницу.
  await expect(page.locator('.dashboard-item')).toBeVisible();
});
Use code with caution.


Пример 3. Мутация статус-кода (Эмуляция падения API)
Проверим, умеет ли тест обрабатывать критические ошибки сервера (500 Error).

javascript
test('Проверка теста на падение сервера (500)', async ({ page }) => {
  // Превращаем любой запрос к корзине в ошибку 500
  await page.route('**/api/v1/cart/add', route => {
    route.fulfill({
      status: 500,
      contentType: 'application/json',
      body: JSON.stringify({ error: "Internal Server Error" })
    });
  });

  await page.goto('/shop');
  await page.locator('.add-to-cart-btn').click();

  // Хороший тест должен проверить появление сообщения об ошибке для пользователя.
  // Если тест просто кликает и считает, что все ок — он не надежен.
  await expect(page.locator('.error-notification')).toContainText('Ошибка при добавлении');
});
Use code with caution.


С чего начать автоматизацию таких проверок?
Вы можете создать отдельный тестовый suite под названием mutation.spec.ts. В нем вы берете ваши основные UI-сценарии, но перед каждым шагом через page.route() умышленно портите ответы сервера. Ваша цель — убедиться, что каждый тест в этом файле завершился ошибкой (Failing). Если какой-то тест завершился успешно (Passed) — вы нашли слепую зону.
