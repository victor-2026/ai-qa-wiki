# Living Documentation + Moldable Development — JIT learning/onboarding directions

**Источник:** пользовательский материал (2026-09-18). Два подхода + связка, для вики и детализации подходов (Just-in-Time обучение, ускорение онбординга).

---

## 1. Living Documentation (Живая документация)

- **Определение:** документация генерируется автоматически из кода, тестов и конфигураций — не пишется отдельно в Word/Wiki. «Живая»: обновляется в ту же секунду, когда меняется код. Упавший тест помечает функцию как нерабочую.
- **JIT Learning:** не нужно искать устаревшие гайды — точная информация в момент работы. Тесты = executable specifications, гарантированно рабочие примеры.
- **Книга:** Living Documentation, Cyrille Martraire. Принципы: официальная страница книги. Инструмент-пример: Cucumber & BDD (https://cucumber.io/docs/bdd/) — Gherkin как executable specs.

## 2. Moldable Development (Гибкая разработка)

- **Определение:** философия Тудора Гирбы (Tudor Gîrba) — разработчик создает кастомные инструменты под конкретную проблему вместо стандартной IDE «как есть». Вместо часов textual reasoning — скрипт, визуализирующий код (диаграмма/карта/граф) под текущий вопрос.
- **Восприятие:** «лепишь» (mold) визуальный ответ («как 50 микросервисов связаны прямо сейчас») — ниже когнитивная нагрузка, мгновенное понимание.
- **Флагман:** Glamorous Toolkit (gtoolkit.com). Манифест: https://moldabledevelopment.com/ (+ доклад Гирбы на YouTube).

## Связка (из материала)

Living Documentation гарантирует верность данных (факты), Moldable Development дает линзу (визуализацию) для мгновенного считывания. Вместе: изучение системы из «археологии» в инженерную задачу.

## Иллюстрация (пример: новичок и сломанный логин)

Новый разработчик в проекте на миллион строк. Вопрос: «где ломается логин?»

**Без подходов (археология):** недели в устаревшем Confluence, построчное чтение чужого кода, расспросы старожилов. Каждый ответ надо перепроверять — а правда ли это еще так.

**С ними (инженерия):**
- Living Documentation = факты, которым можно верить. Вместо годовалой статьи — живой отчет из тестов прямо сейчас: цепочка вызовов, что зеленое, что красное. Упавший тест сам красит строчку в красный. Врать не может по построению.
- Moldable Development = линза под вопрос. Скрипт за 20 минут рисует именно граф вызовов логина — не весь проект, а ответ на свой вопрос. Посмотрел — понял.

**Мораль:** факты без линзы — простыня логов (правда, но нечитаемо). Линза без фактов — красивая картинка вчерашнего дня (читаемо, но вранье). Пара дает «правду, которую видно сразу»: система сама говорит, что в ней правда, а ты мастеришь удобные очки, чтобы на нее посмотреть.

- Executable specs (Gherkin/Cucumber) ↔ evidence lineage: спецификация, которая выполняется = спецификация, которой можно верить. Рядом с metamorphic-тестами Bach и BDD-скиллом.
- Moldable tooling ↔ Bach (purpose-built tools за 5–20 минут через agentic coding) ↔ Davidov progressive disclosure: инструмент под вопрос, а не платформа под все.
- Living docs как антидот config rot (Osmani): документация, генерируемая из кода, не протухает по построению.
