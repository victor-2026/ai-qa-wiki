# How to Test the Auth Code an AI Agent Wrote

- **Source:** https://getautonoma.com/blog/testing-ai-generated-auth-code
- **Author:** Tom Piaggio, Co-Founder at Autonoma
- **Date:** June 2026

## Key thesis

When an AI agent writes your authentication, there is **no human baseline for what correct behavior looks like** — the agent pattern-matched on millions of login implementations but was never given a behavioral spec. So define expected auth behavior explicitly: valid users log in, invalid credentials are rejected, protected routes redirect. Then verify the AI-generated code against that spec with end-to-end tests.

The 2026 recurring retrospective story: AI coding agent drops an auth wrapper, code compiles, code review passes, users hit a locked-out production app. Pattern is structural, not a fluke.

## Why AI-written auth has no baseline

- A human engineer carries an informal spec in intuition: valid user → dashboard, wrong password → error, logged-out user + protected route → login page.
- An AI agent has no such intuition about *your* application. It generates code that looks correct, uses right library calls, returns reasonable status codes. It never verifies behavior matches your needs.
- Tests generated by the same agent or its peer derive from the same implementation → assert the code back to itself. Wrong assumption → wrong expected value → test passes.
- Auth amplifies the general "no baseline" problem ([regression testing AI-generated code](/blog/regression-testing-ai-generated-code)): no previous implementation to diff against, failure mode is catastrophic rather than gradual.

## Defining expected auth behavior (3 questions → behavioral contract)

1. **Who can log in, and what do they reach?** Standard user → dashboard, admin → admin panel, deactivated user → no access. Each = distinct test case.
2. **What should fail, and how?** Wrong password, expired token, unregistered email, locked account. Each failure mode → correct error message, correct HTTP status, no accidental session creation. AI code often handles happy path well, failure modes inconsistently.
3. **What do protected routes actually protect?** Logged-out user → redirect to login, not served page with blank state. Wrong role → authorization error, not limited-data page. These guard behaviors are what AI agents silently omit — wrapper looks like boilerplate and gets dropped.

| Behavior to define | Expected outcome | Failure mode to test |
|--------------------|------------------|----------------------|
| Valid user logs in | Reaches correct destination | Wrong destination, blank state |
| Wrong password | Error shown, no session created | Error silent, session exists |
| Unregistered email | Specific error, no session | Generic error, info leak |
| Logged-out user hits protected route | Redirects to login | Serves page, no redirect |
| Authed user reaches protected route | Renders correct content | Auth loop, blank page |

The spec is the behavioral contract the AI code must satisfy. The AI's code is implementation detail.

## Why verify end-to-end, not unit-by-unit

Auth behavior only exists in the context of a running application. A unit test confirms the function returns a token for valid credentials. It cannot confirm: token passed to session layer, session sets cookie, middleware reads cookie, protected route checks middleware. A dropped auth wrapper is invisible to any unit test — it's not a function that gets called, it's a guard supposed to surround the route.

E2E drives a real browser: navigate `/login`, submit, assert URL and visible content. Assertions are simple; their value is being derived from the behavioral spec, not the AI-generated code.

## Autonoma's positioning (vendor angle)

Planner reads routes/components/user flows → establishes behavioral spec from intended architecture, independent of the PR that introduced the AI auth code. Executor runs against live preview in real browser. Reviewer separates real auth bug from agent error / test mismatch. Diffs Agent maintains coverage on subsequent PRs. Catches exactly: valid login that silently fails, protected route that doesn't redirect, wrong-password case that creates a session anyway.

- Same independence theme as `copilot-generated-tests-quality-pitfalls`: AI-verification is only trustworthy when independent from the thing being verified. Auth = highest stakes.
- Directly maps to our Buzzhive auth suite (login flows, role-based access, banned user, admin/mod role tests) and Go Antigravity login API tests (SQL injection, boundary).
