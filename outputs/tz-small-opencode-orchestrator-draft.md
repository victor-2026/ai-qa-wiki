# ТЗ: точечное внедрение паттернов small-opencode-orchestrator (на обсуждение окон)

**Источник:** `tempont/small-opencode-orchestrator` (33★, 8 форков, 20 коммитов, активен до 28.09.2026, MIT). Русскоязычный разбор: https://ai4coding.ru/solutions/tempont-small-opencode-orchestrator (04.06.2026; отмечает v1.1.0: разделение прав записи, обновленные конфиги, уточненный роутинг).
**Альтернативы (не оценивались, для полноты картины):** `oh-my-opencode-slim` (мультиагентная оркестрация), `OpenChamber` (рантайм-контроль с устройств), "OpenCode vs Claude Code" (23.09.2026) — все via ai4coding.ru. Плюс из экосистемного обзора: Oh My OpenCode / Sisyphus (`ultrawork`, инженер-менеджер + спецагенты), OpenCode Orchestrator Kit (строгий no-edit оркестратор, дешевые локалки на анализ, frontier только на патч/ревью), FlowDeck / Open Conclave (визуальные дашборды графа задач).

Забрать 4 точечных паттерна (критик планов, разделенные ревью, таблица делегации, роутинг моделей), не ломая текущие связки (free-first, `muse-spark`, bot.py simple/complex).

## 5. bot.py: сплит simple/complex
- По умолчанию: как сейчас (`build`/`qa`).
- `/agent orchestrator` только для сложных задач. Эвристика сложности: длинный запрос / слова "план", "реализуй", многошаговость.
- Причина: оркестратор на каждый one-shot запрос = +latency и расход Go-квоты.

## 6. Критерии приемки (все — да/нет)
1. Ни один существующий конфиг/агент не перезаписан (diff `~/.config/opencode` до/после — только добавления).
2. Critic находит ≥1 дефект плана на тестовом плане (демо-кейс; владелец: окно-исполнитель пилота, TBD).
3. 3-проходное ревью ловит то, что один `reviewer` пропускал (1 демо-кейс; владелец: окно-исполнитель пилота, TBD).
4. Простой запрос в bot.py идет старым путем (latency не выросла).
5. Free-first не нарушен: платные модели только на координацию/план.

## 7. Порядок + владельцы (предложение, обсуждается)
1. Копия 4 файлов во временную папку (не в конфиг) — исполнитель по назначению.
2. Ремаппинг моделей + адаптация ревью под Playwright.
3. Пилот на 1 задаче → демо → решение о постоянке.
4. bot.py-сплит — последним, после доказательства 1–3.

## 8. Риски
- Затирание конфига при установке целиком (запрет в п.3).
- Рост latency/квот в боте (лечится сплитом п.5).
- Платный дрейф: сильные модели расползаются на исполнение (лечится роутингом п.4 + guard лимитов).
- Секреты в делегации (W2): оркестрованные субагенты множат поверхность утечек — секреты не входят в делегированный контекст; либо явное redaction-правило до внедрения.
- Открытый вопрос (W2): фаерят ли хуки на tool-вызовы субагентов? Проверить до опоры — иначе делегированные записи обходят гарды молча.

## 9. Подробности (границы применимости)

### Оркестрация: где поможет
- Сложные многошаговые задачи: план → критик → исполнение порциями → 3 ревью (закрывает "автор не экзаменатор").
- Параллельные независимые проходы; повторяемые пайплайны (пилоты, волны ингеста).

### Оркестрация: где не пригодится
- One-shot простые запросы (оверхед latency + квота — покрыто сплитом п.5).
- Плотно интерактивные задачи (фазовый approval = турникет).
- Решения вкуса владельца, а не процедуры.

### Субагенты (pi-subagents): где помогут
- Параллельная разведка (scout/researcher), спецпроверки (reviewer ловил P0), исполнение с handover (worker).
- Тяжелый рид без засорения главного контекста.

### Субагенты: где не пригодятся
- Последовательные зависимые шаги (handover теряет живой контекст).
- Дешевые быстрые ответы (спавн дороже ответа).
- Вкус/решения владельца; секреты в контексте (границы окон тоньше).

### PRD-шаблон
- Отдельного PRD-скилла нет; ближайшее — `superpowers` (/brainstorm → /write-plan → /execute-plan) и пример `weekly-time-planner-prd-example.md` в wiki. Приемка п.6 — наполовину PRD; полный шаблон — отдельной задачей при запросе.

### Топологии (из экосистемного обзора, на случай если зацикливание когда-то примут)
| Схема | Суть | Вердикт для нас |
|-------|------|-----------------|
| Flat Fan | Оркестратор снаружи, глубина 1, параллельные изолированные задачи | Единственная приемлемая: нет infinite loops, параллельные ревьюеры |
| Evaluator-Optimizer | Оптимизатор генерит → валидатор проверяет (MCP тесты/линт) → возврат с логами | Для багфиксов/рефакторинга, автономного закрытия простых Issue |
| Hierarchical Swarm | Вложенность без ограничения | Нет: в OpenCode нет circuit breaker — съест баланс |

### Shared Brain (память как координация)
- Оркестратор держит скрытую папку (`.context/` / `.opencode/memory/`); каждый субагент пишет туда краткий Markdown-отчет (что сделано, файлы, интерфейсы); следующий подтягивает отчет вместо истории переписки (инструменты типа Recallium/Honcho). Наш аналог де-факто: handover текстом + чекпоинт как шина. При принятии зацикливания — формализовать этим паттерном.

## 10. Решение W1 (12eed0c) — берем без оркестрации
- Оркестрацией является только автоматическое зацикливание (план→критик→исполнение→ревью без рук). Все 4 пункта отделяемы — "не вводим оркестрацию" стоит 0 из 4.
- Порядок: критик планов первым и отдельно (highest ROI, закрывает класс "ошибка поймана постфактум"), затем разделенные ревьюеры, таблица делегации (документ, ноль инфры), роутинг моделей. Зацикливание — когда-нибудь потом, если вообще.
- Субагенты: текущий паттерн держать в границах п.9 (доказано: параллельная разведка, спецпроверки P0, тяжелые риды; границы: зависимые цепочки, дешевые ответы, вкус владельца, секреты).

**Доказано тестами:**
- Проза с триггер-словами проходит; голые commit/push, `add -A`, чужие файлы, `commit -a`, смешанный стейдж — блочатся (10/10 unit + live).
- Хуки файерят на tool-вызовах субагентов (пробный коммит Task-сабагента заблокирован дословно) — делегированные записи гарды молча не обходят (открытый вопрос W2 закрыт).
- Fail-closed везде: непонятное = блок + маркер.

**Процедуры из боя:** рутинный covered-коммит = `add`+`commit` в одном вызове (стейджинг ≠ запись контента); heredoc-записи контента — отдельно от истории; маркер только по явному слову владельца (кроме standing cover).
