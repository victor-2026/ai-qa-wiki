## What AI‑Generated Tests Keep Getting Wrong (2024‑2026)

**Author:** Lucio Daza (Product Marketing, Testkube) – with the Testkube team and CTO Ole Lensmar  
**Source:** [Ministry of Testing – MoT Moment](https://www.ministryoftesting.com/moments/what-ai-generated-tests-keep-getting-wrong-and-what-finally-fixed-it-for-us)  

### Summary
AI assistants can spit out syntactically correct test code in seconds, but the code often **asserts against its own mocked environment** instead of the real system under test. Because the generated test looks plausible, reviewers merge it without noticing the hidden mock, leaving a “green‑only” test that never fails—even when the production feature breaks. The root cause is that tests are highly specific to a particular service, endpoint, payload, and environment, while LLMs only have generic knowledge. The fix is not a smarter model but a **verification‑first workflow**: run the generated test against a real environment before it is accepted. If it survives this quick sanity check, it earns a place in the suite; otherwise, the model’s guesses are caught instantly.

### Key Concepts  

| Concept | Explanation |
|---------|-------------|
| **Domain‑specificity of tests** | A test encodes concrete claims (service name, URL, request shape). General‑purpose code generation cannot reliably fill these gaps. |
| **Plausible‑guess hazard** | When the model does not know the system, it inserts believable but incorrect values (e.g., mock objects). These pass code review because they look correct. |
| **Failure mode 1 – “Wrong‑break”** | The test crashes for unrelated reasons, wasting developer time fixing generated code. |
| **Failure mode 2 – “Silent‑pass”** | The test always passes because it never touches the real system, giving a false sense of coverage. |
| **Verification‑first principle** | A generated test must be executed against a real (un‑mocked) target **before** it is merged. “Looks right” provides no evidence. |
| **Testkube’s draft‑run PR flow** | • Write a test in plain language. <br>• Choose any framework (Selenium, Playwright, load‑test, etc.). <br>• The AI creates the code and immediately runs it in the user’s own infra. <br>• Only after a successful run is a PR opened. |

### Practical Applications  

1. **Integrate AI test generation into CI pipelines**  
   - Trigger the AI step, capture the draft test, spin up a short‑lived environment (e.g., a staging namespace), and execute the test.  
   - If the run fails, surface the error to the author for correction; if it passes, automatically open a pull request.

2. **Enforce “no‑mock‑by‑default” policy**  
   - Scan generated code for mock imports or stub definitions. Flag any test that does not reference a real endpoint or service.

3. **Use the approach for all test types**  
   - Functional UI tests, API checks, load‑testing scripts, and infrastructure validation can all benefit from the immediate‑run guardrail.  

4. **Combine with mutation testing**  
   - After a generated test is merged, run mutation analysis to confirm it would fail if the underlying behavior changed, reinforcing the verification‑first mindset.

5. **Educate reviewers**  
   - Train QA engineers to treat “looks correct” as **no evidence**. Require a passing run log or a screenshot from the execution environment as part of the review checklist.

### Recommendations for Teams  

- **Adopt a draft‑run workflow** (e.g., Testkube, custom scripts) for any AI‑generated test.  
- **Lock down mock usage**: only allow mocks when explicitly required and documented.  
- **Log execution artifacts** (request/response, environment details) alongside the PR for auditability.  
- **Iterate on prompts**: include “run against real service X” in the request to the LLM to reduce guesswork.  
- **Measure coverage impact**: compare defect detection rates before and after adopting verification‑first to quantify benefits.
