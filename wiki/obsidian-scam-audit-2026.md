## Obsidian Scam – Fake QA Audit Using Malicious Community Plugins  

**Date:** 24 June 2026 **Source:** Personal experience  

---  

### Summary  
A social‑engineering campaign pretended to be a paid QA audit. The attacker supplied an Obsidian Sync account and asked the victim to enable community plugins. Two hidden plugins – **Hider** and **Shell Commands** – were then used to steal vault data, execute arbitrary code on the victim’s machine, and maintain persistence through the shared sync account. The scheme illustrates how trusted‑looking productivity tools can become a supply‑chain attack vector when plugins are installed without verification.  

---  

### Key Concepts  

| Concept | Explanation |
|---------|-------------|
| **Community plugins** | Extensions written by third parties. Obsidian only performs lightweight vetting, so malicious code can slip through. |
| **Hider** | Alters the UI to conceal settings, warnings or other plugins, making malicious activity less visible. |
| **Shell Commands** | Grants the ability to run system commands under the user’s privileges; can be triggered automatically on vault open or via URI links. |
| **Sync account abuse** | Sharing login credentials gives the attacker full control over what is synced, enabling remote updates of malicious plugins. |
| **Sandboxing** | Running untrusted vaults inside an isolated environment (VM, container, or air‑gapped device) to limit damage. |
| **Restricted Mode** | Obsidian’s built‑in safeguard that blocks community plugins unless explicitly enabled. |

---  

### Practical Applications  

1. **Security testing of knowledge‑base tools** – Use this case as a checklist when evaluating any platform that supports third‑party extensions.  
2. **Incident response** – If a vault is compromised, immediately:  
   - Revoke the shared Sync session and change passwords.  
   - Remove the suspicious plugins from the vault.  
   - Scan the host for artifacts left by executed commands.  
3. **Policy enforcement** – Enforce “no external plugins unless vetted” rules in teams that rely on Obsidian for documentation.  
4. **Training** – Demonstrate the attack flow (social engineering → credential sharing → plugin installation → RCE) in security awareness programs.  

---  

### Defense Recommendations  

1. **Never install plugins from unknown sources** – Treat every community plugin as potentially hostile.  
2. **Keep Restricted Mode enabled** – Only toggle it for plugins that have been audited.  
3. **Isolate suspicious vaults** – Open them in a disposable VM or container; mobile Obsidian cannot run Shell Commands, providing a quick air‑gap test.  
4. **Never use another person’s Sync account** – Shared credentials give the attacker control over future syncs.  
5. **Monitor plugin activity** – Periodically review the list of enabled plugins and their permissions.  
6. **Post‑exposure hygiene** – Rotate all passwords, revoke OAuth tokens, and audit audit logs for unexpected access.
