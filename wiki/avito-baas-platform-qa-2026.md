## QA платформы BaaS в Avito: подходы, архитектура, инсайты

### О чём статья
Avito построил платформу **BaaS (Backoffice as a Service)** — конструктор для внутренних продуктов. Десятки команд используют её как фундамент. Статья — про то, как QA-инженер тестирует не конечный продукт, а **платформенные обещания**: авторизацию, права, маршрутизацию, конфигурации.

---

### Ключевые принципы

| Принцип | Суть | Пример |
|---------|------|--------|
| **Начинать не с кнопок, а с рисков** | Карта critical scope — не список экранов, а зоны качества | Вместо «проверить страницу» → «что будет, если BaaS сломается в этой зоне» |
| **Слабые vs сильные проверки** | Слабая: «настройка сохранилась». Сильная: «настройка изменила поведение» | Проверить не факт записи права, а то, что пользователь получил нужный доступ |
| **Проверять эффект, а не факт сохранения** | Config меняет runtime — проверяем runtime | До/После: зафиксировали поведение → изменили конфиг → проверили новое поведение |
| **Изоляция тестовых данных** | Уникальные сущности + идемпотентность | Тест выдерживает повторный запуск без ручной чистки |
| **Автоматизация не всё** | Новый/нестабильный сценарий → сначала руками | Автоматизировать только когда повторяемо, риск понятен, результат стабилен |

---

### Риск-карта: 7 зон качества

| Зона качества | Что может пойти не так |
|---------------|----------------------|
| Подключение продукта | Создан, но не работоспособен (нет доступа, настроек) |
| Вход пользователя | Пользователь не может войти или получает лишний доступ |
| Права и ограничения | Пользователь видит/теряет функции после изменения настроек |
| Настройки и конфигурации | Запрос не доходит до нужного продукта/сервиса |
| Конфигурация (runtime) | Настройка сохранилась, но не изменила поведение |
| Стабильность сценариев | Релиз сломал работающие продукты |
| Негативные сценарии | Ошибка оставляет систему в неоднозначном состоянии |

---

### Архитектура тестирования BaaS (9 уровней)

| Уровень | Что проверяет | Техника |
|---------|--------------|---------|
| **1. Unit + Mutation** | Логика обработки данных | Mutation Score — искусственно ломаем код, проверяем, что тесты падают |
| **2. Contract (интеграция)** | Стыки компонентов, формат данных | Pact-тесты, граничные классы |
| **3. Config Integration (До/После)** | Реальный эффект настройки в runtime | 5 шагов: изолировать → выполнить → проверить → проверить отказ → проверить состояние |
| **4. Data Idempotency** | Повторный запуск, изоляция | Уникальные сущности, префиксы, очистка |
| **5. E2E (точечно)** | Критические path целиком | Только атомарные critical paths |
| **6. Post-release monitoring** | Поведение в проде с реальными данными | Технические + продуктовые метрики |
| **7. Load testing** | Пределы при росте нагрузки | Точка деградации, узкие места |
| **8. Chaos testing** | Поведение при сбоях инфраструктуры | Таймауты, недоступность зависимостей, частичные сбои |
| **9. Manual (исследовательское)** | Новые/нестабильные сценарии, UX | Пока сценарий не стал повторяемым |

---

### 3 уровня проверки конфигурации

1. **Структурная валидность** — можно ли технически принять (поля, типы, ошибки)
2. **Платформенная консистентность** — не противоречит ли правилам и связям
3. **Runtime-эффект** — изменилось ли реальное поведение (До/После)

### Анализ для подготовки к собеседованию Avito Test Lead

Статья написана инженером платформенной команды (не Monetization), но отражает **культуру качества Avito**. Вот что из статьи прямо применимо к вашему кейсу (MNZ, защита 08.07):

**1. Case defense: Team 3 (platform)**
В кейсе есть команда №3 — платформа с неизвестным качеством. Статья даёт готовый подход:
- Построить **карту рисков** (как 7 зон качества) вместо инвентаризации тестов
- Внедрить **contract testing** на стыках (Team 1 — backend aggregator, идеальный кандидат)
- Использовать **mutation score** для оценки реального покрытия (Team 2 — много багов, mutation покажет слепые зоны)

**2. Ответ на вопрос «какие метрики» — добавьте из статьи:**
- **Mutation Score** — доля пойманных мутаций. Если unit-тесты зелёные при мутации — они бесполезны
- **Outdated rate** (из Habr-статьи про Code Review) — процент комментариев, закрытых исправлением
- **«Эффект, а не факт»** — метрика: сколько настроек реально изменили поведение (не просто сохранились)

**3. Go-подготовка — добавьте:**
- В статье Go — основной язык платформы (Go-сервис оркестрирует ревью в Habr-статье)
- Contract testing, интеграционные проверки — на Go
- Вспомнить: `httptest.Server`, `testify/suite`, table-driven tests с подходами из статьи

**4. DS/ML-тестирование:**
- «Алгоритмы распределения ликвидности» в MNZ — mutation testing на уровне данных
- Chaos testing для ML: что если фиче-стор недоступен?

**5. Что добавить в ответ про TDR (Tech Design Review):**
- В статье: «проверка эффекта, а не факта» — это и есть TDR-мышление
- На TDR спрашивать: «как мы узнаем, что конфигурация реально изменила поведение?»

**6. Фразы, которые стоит использовать в ответах:**
- «Платформенное качество нельзя сделать один раз — его приходится постоянно пересобирать»
- «QA на уровне платформы — это не про написать побольше автотестов, а про систему доверия»
- «Мы проверяем не отдельные кнопки, а доверие к платформенному слою»
- «Чем больше связей между сценариями, тем выше шанс, что тест упадёт не из-за бага, а из-за подготовки данных»
