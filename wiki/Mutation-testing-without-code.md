# Мутационное тестирование без доступа к коду

## Обзор
Мутационное тестирование — это техника проверки **качества и надежности автотестов**, а не самого продукта. Вместо проверки функциональности системы мы оцениваем, насколько тесты способны обнаруживать намеренно внесенные дефекты.

## Как работает классическое мутационное тестирование
1. Инструмент автоматически вносит мелкие умышленные ошибки (мутации) в исходный код
2. Измененная версия называется «мутантом»
3. Запускаются существующие тесты на этом мутантном коде
4. Анализ результатов:
   - **Мутант убит**: хотя бы один тест упал → тесты бдительны (хорошо)
   - **Мутант выжил**: все тесты прошли → тесты имеют слепые зоны (плохо)

## Примеры операторов мутации (изменения в коде)
- **Замена знаков**: `>` → `>=`, `+` → `-`
- **Изменение логики**: `if (a && b)` → `if (a || b)`
- **Подмена возвращаемых значений**: `return true;` → `return false;`

## Проблема в легаси-системах
Классические инструменты мутационного тестирования (Stryker Mutator, PITest, Mutmut) требуют:
- Исходного кода
- Доступа к процессу сборки/скомпилированному байт-коду

Это делает их неприменимыми для закрытых систем или легаси-проектов без доступа к коду.

## Альтернативные подходы для черного ящика
Когда доступ к коду невозможен, мутируем не код, а:

### 1. Фатчинг / Фаззинг-тестирование (Fuzzing)
Вместо изменения кода подаем на вход системы:
- Хаотичные данные
- Невалидные входные параметры
- Случайно измененные запросы

**Проверка**: Если тесты не фиксируют ошибок там, где система должна вернуть 500, значит тесты не покрывают негативные сценарии.

### 2. Мутация API-ответов (Сетевое мутационное тестирование)
Для сервисных проектов:
- Перехватываем ответы бэкенда (через прокси типа Charles, Fiddler, Mitmproxy)
- Умышленно портим JSON/XML-пакеты
- Проверяем реакцию тестов на поломку интеграций

### 3. Chaos Engineering (Инженерия хаоса)
Мутируем среду обитания проекта:
- Имитируем задержки сети
- Отключаем базу данных
- Забиваем оперативную память
- Требуем от тестов четкого обнаружения этих падений инфраструктуры

## Полноценный анализ покрытия без кода
Для оценки эффективности тестов в легаси-проекте:
1. Составьте карту всех известных функций системы (Black-box спецификация)
2. Сопоставьте каждый тест с конкретной функцией
3. Функции без тестов = ваши главные «выжившие мутанты»

## Практические сценарии для Веб-сайт + API + БД конфигурации

### Сценарий 1: Мутация данных в БД
**Цель**: Проверить бдительность тестов к поврежденным данным

**Как выполнить**:
1. Запустите автотесты до шага проверки
2. Поставьте тест на паузу
3. Измените значения в тестовой БД:
   - Статус заказа: `New` → `Archived`
   - Баланс пользователя: положительный → `0` или отрицательный
   - Текстовое поле: добавьте спецсимволы (`<script>alert('xss')</script>`)

**Ожидаемый результат**: Тест должен упасть. Если тест прошел — он не замечает поврежденных данных и требует переработки.

### Сценарий 2: Мутация API через прокси
**Цель**: Проверить реакцию UI-тестов на поломку бэкенда

**Как выполнить** (с UI-тестами типа Selenium, Playwright, Cypress):
1. Перехватывайте API-запросы между UI и бэкендом
2. Мутируйте ответы «на лету»:
   - Смените статус-код: `200 OK` → `500 Internal Server Error`
   - Удалите обязательное поле из JSON (например, `id` или `price`)
   - Замените числовое значение на `null`

**Ожидаемый результат**: UI-тесты должны упасть с понятной ошибкой (alert, падение элемента), а не зависать по таймауту.

### Сценарий 3: Фаззинг API
**Цель**: Проверить устойчивость API-тестов к некорректным запросам

**Как выполнить** (для тестов в Postman или подобных):
1. Используйте облегченные фаззеры или сканеры уязвимостей (OWASP ZAP, Burp Suite)
2. Инструмент берет структуру легаси-запроса и подменяет параметры:
   - Экстремально длинные строки
   - SQL-инъекции
   - Бинарные файлы

**Ожидаемый результат**: API-тесты должны падать с ошибкой валидации (`400 Bad Request`), подтверждая, что они distinguish корректную работу от аварийной.

## Автоматизация с Playwright
Playwright предоставляет встроенную мощную систему перехвата сетевых запросов, идеально подходящую для имитации мутаций бэкенда.

### Пример 1: Мутация данных (Изменение JSON-ответа)
```javascript
import { test, expect } from '@playwright/test';

test('Проверка теста на подмену данных (Цена = 0)', async ({ page }) => {
  // 1. Внедряем МУТАЦИЮ: перехватываем запрос к API и меняем цену на 0
  await page.route('**/api/v1/products/*', async route => {
    const response = await route.fetch();
    const json = await response.json();
    
    // Мутируем поле цены
    json.price = 0; 
    
    // Отправляем измененный JSON обратно в браузер
    await route.fulfill({ response, json });
  });

  // 2. Выполняем обычные шаги теста
  await page.goto('/products/123');

  // 3. Ожидаемый результат: ТЕСТ ДОЛЖЕН УПАСТЬ!
  // Если у вас стоит проверка, что цена отображается корректно, 
  // то этот ассерт завалится. Если тест прошел — значит, он написан плохо.
  await expect(page.locator('.product-price')).toHaveText('$99.99');
});
```

### Пример 2: Мутация структуры (Удаление обязательного поля)
```javascript
test('Проверка теста на отсутствие поля в API', async ({ page }) => {
  await page.route('**/api/v1/dashboard', async route => {
    await route.fulfill({
      status: 200,
      contentType: 'application/json',
      body: JSON.stringify({ 
        user: "Иван", 
        // Поле items умышленно удалено (мутация)
      })
    });
  });

  await page.goto('/dashboard');

  // Тест должен упасть на проверке элементов интерфейса, 
  // а не зависнуть или показать пустую "зеленую" страницу.
  await expect(page.locator('.dashboard-item')).toBeVisible();
});
```

### Пример 3: Мутация статус-кода (Эмуляция падения API)
```javascript
test('Проверка теста на падение сервера (500)', async ({ page }) => {
  // Превращаем любой запрос к корзине в ошибку 500
  await page.route('**/api/v1/cart/add', route => {
    route.fulfill({
      status: 500,
      contentType: 'application/json',
      body: JSON.stringify({ error: "Internal Server Error" })
    });
  });

  await page.goto('/shop');
  await page.locator('.add-to-cart-btn').click();

  // Хороший тест должен проверить появление сообщения об ошибке для пользователя.
  // Если тест просто кликает и считает, что все ок — он не надежен.
  await expect(page.locator('.error-notification')).toContainText('Ошибка при добавлении');
});
```

## С чего начать автоматизацию
Создайте отдельный тестовый suite под названием `mutation.spec.ts`:
1. Возьмите ваши основные UI-сценарии
2. Перед каждым шагом через `page.route()` умышленно портите ответы сервера
3. Цель: убедиться, что каждый тест в этом файле завершился ошибкой (Failing)
4. Если какой-то тест завершился успешно (Passed) — вы нашли слепую зону
