## AI-ревью кода через LLM в Avito: архитектура, метрики, полезность

### Что сделали
Avito автоматизировал Code Review через LLM. Система обрабатывает 1000 PR/нед (пик 300/час). Разработчик оставляет комментарий `ai_review` в PR → трёхэтапный ML-пайплайн → комментарии публикуются в Stash.

---

### Архитектура

```
Stash (интерфейс) → Go-сервис (оркестратор, состояния ревью) → Python ML Pipeline
```

Go-сервис: получает diff + метаданные (структура репозитория, существующие комментарии), управляет статусами (STATE_REQUESTED → BackgroundTaskRunner → STATE_FINISHED).

ML Pipeline — 3 этапа:

| Этап | Модель | Задача | Метрика |
|------|--------|--------|---------|
| **RuleChecker** | Qwen3-Coder-30B | Выявить все потенциальные проблемы (высокий recall, низкая precision) | Покрытие 4 классов |
| **ReviewFilter** | Та же модель, второй проход | Отсеять false positives (Conclusion First) | Убирает 90% галлюцинаций |
| **CommentAggregator** | BAAI/bge-m3 (эмбеддинги) | Дедупликация по cosine similarity > 0.85 | Группировка семантически близких |

4 класса проблем: безопасность, дефекты разработки, перфоманс, поддержка кода.

---

### Выбор модели

| Критерий | Gemini 2.5 Flash | Qwen3-Coder-30B-FP8 |
|----------|-----------------|-------------------|
| MERA-RuCodeReviewer | #1 | #2 (выбран) |
| Self-host | Нет (API) | Да ✅ |
| Безопасность кода | Передача вовне | Внутренний контур ✅ |
| Экономика | Дорого (2K-10K токенов/PR) | Существенно дешевле ✅ |

Две причины self-hosting: **безопасность** (код не уходит вовне) и **экономика** (токеноёмкие генерации, self-host кратно дешевле API).

---

### Производительность

- Малые PR (≤3 файла): 10-20 сек
- Большие PR (10+ файлов): ~60 сек
- Параллельность: до 650 ревью одновременно (с запасом на расширение)

---

### Метрики качества

| Метрика | Значение | Что означает |
|---------|----------|--------------|
| **Precision** | 85% | 85% комментариев пользователи оценивают лайком |
| **Outdated rate** | 32% overall, 60% Infra/DevOps | Комментарий закрыт исправлением кода — реальная польза |
| **False positives отсечено** | 90% | ReviewFilter убирает 9 из 10 галлюцинаций |

---

### Выводы для QA / Тестирования LLM

1. **RuleChecker → ReviewFilter — паттерн для LLM-тестирования.** Сначала максимальный захват (высокий recall), потом фильтрация (precision). Аналогия: mutation testing (RuleChecker) → код-ревью (ReviewFilter).

2. **«Не стоит решать всё одним запросом».** Даже с длинным контекстом модель теряется. Разделение на этапы — ключевой архитектурный принцип.

3. **ReviewFilter убирает 90% галлюцинаций** — это важнейшая цифра: LLM-as-a-Judge требует второго прохода валидации.

4. **Self-hosting окупается при объёме.** Если генерации токеноёмкие (2-10K токенов на запрос) и частота высокая (1000 PR/нед), self-host выгоднее API.

5. **Outdated rate 32%** — метрика, применимая к LLM-тестам: процент замечаний, которые действительно ведут к исправлению кода. Аналог Actionable Rate в LLM testing.

6. **BAAI/bge-m3 для дедупликации** — практический пример эмбеддинг-модели для семантической близости в пайплайне.

7. **4 класса проблем** (безопасность, дефекты, перфоманс, supportability) — готовая таксономия для чеклиста code review при тестировании LLM-агентов.

### Полезность для практики

Высокая. Статья показывает production-ready архитектуру LLM-агента с:
- production метриками (85% precision, 32% outdated rate)
- конкретным выбором модели и обоснованием (Qwen vs Gemini)
- трёхэтапным пайплайном, применимым к любым задачам LLM-генерации
- цифрами производительности (10-60 сек на PR, 650 параллельных)
- честным признанием: «скидывать процесс на AI без надзора нельзя»

Наиболее ценный инсайт: разделение генерации и валидации — не просто best practice, а необходимость. ReviewFilter как отдельный этап убирает 90% мусора, без него система была бы бесполезной.
