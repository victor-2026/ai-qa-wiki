## Filip Hric — Playwright CLI + Jev vs Playwright MCP (2026‑09‑25)

**Author:** Filip Hric – Playwright educator and AI‑testing advocate.  
**Source:** LinkedIn post (user‑pasted, 1 h old). The video linked in the post is behind a LinkedIn gate and was not retrieved. All figures are the author’s own measurements and have not been independently verified.

### Summary
In a short experiment the author compared two ways of turning a vague user instruction into UI actions on a Trello‑style demo app:

| Approach | Decision flow | Execution |
|----------|---------------|-----------|
| **Playwright MCP (baseline)** | Snapshot → LLM decides which element to act on → tool‑call loop (Astra model) → Playwright executes | Multi‑step agent loop, each step incurs LLM token cost and latency. |
| **Playwright CLI + Jev** | Snapshot → Jev (a judgment‑model) directly selects the target element → Playwright CLI runs the command | Single‑shot verdict, no intermediate tool calls. |

For the fuzzy command *“Create new board, list and card”* the Jev‑driven path was reported to be **≈98 % cheaper** and **≈2 × faster** than the MCP loop. The author notes that the Jev path could be further optimized.

### Key Concepts
| Concept | Explanation |
|---------|-------------|
| **Judgment‑as‑Locator** | A “verdict” model (Jev) receives a UI snapshot and instantly decides which DOM element satisfies a high‑level instruction, bypassing the classic LLM‑tool‑call cycle. |
| **Playwright CLI** | A command‑line interface that can execute Playwright actions directly from a concise description, suitable for one‑shot verdicts. |
| **MCP (Model‑Centric Playwright)** | The standard agent architecture where each decision is delegated to an LLM (e.g., Astra) that may invoke external tool calls before the action is performed. |
| **Tier‑Model Economics** | The cost/latency trade‑off between a multi‑step “loop” model (higher tier) and a single‑shot judgment model (lower tier). The experiment provides a concrete data point (≈98 % cost reduction, 2× speedup) for this axis. |
| **Fuzzy Instruction** | A natural‑language command that does not specify exact selectors; the system must resolve the intent to a concrete UI element. |

### Practical Applications
1. **Locator‑Drift Mitigation**  
   - In projects such as *FlowScout* (deep navigation) and *QAEverest* (ID drift), the ability to resolve a fuzzy instruction to the correct element without a tool‑call loop can dramatically reduce flakiness caused by changing selectors.

2. **Cost‑Effective Test Generation**  
   - For large‑scale regression suites, replacing per‑step LLM calls with a single verdict model can cut cloud‑LLM spend by an order of magnitude, making AI‑augmented testing viable for tighter budgets.

3. **Speed‑Critical CI Pipelines**  
   - The 2× latency improvement means faster feedback cycles, especially valuable in continuous‑integration environments where each test run is time‑sensitive.

4. **Design of Gate‑Based Testing Frameworks**  
   - The structural contrast between MCP (snapshot → LLM → tool) and Jev (snapshot → verdict) offers a blueprint for building “gate” layers that first attempt a one‑shot judgment and fall back to the full agent loop only when confidence is low.

5. **Benchmarking and Model Selection**  
   - The experiment serves as an independent, vendor‑agnostic data point for evaluating the economic viability of judgment models versus full‑blown agent loops in future benchmark suites.

### Caveats & Open Questions
- The measurement is a **single‑task, n = 1** experiment; results may vary across applications, UI complexity, or language models.  
- Details such as token counts, exact prompt templates, and hardware configuration were not disclosed; a deeper dive into the linked video would be needed for reproducibility.  
- The “optimizable further” comment suggests that the reported 98 %/2× gains are a lower bound; systematic tuning could shift the economics even more.
