## Qodo: Adaptive Router for Code‑Review Depth  

**Date:** 23 Sep 2026 – *Qodo* (formerly Codium) is an AI‑driven code‑quality and governance platform. The “Review Effort Modes” feature lets the system decide, per pull request (PR), how much AI scrutiny to apply, balancing review quality against cost and latency.

### Summary  
Traditional AI reviewers treat every PR equally, charging the same credits regardless of risk. Qodo’s new router examines each diff before the review starts, selects an appropriate effort tier, and only spends the resources needed to achieve the best possible F1‑score (precision + recall) for the given cost budget. The objective is:

\[
\max\bigl(F1 - \lambda \cdot \text{cost}\bigr)
\]

where **λ** controls frugality. The router therefore preserves quality while avoiding unnecessary model calls, which also reduces latency.

### Key Concepts  

| Concept | What it means | Why it matters |
|---------|---------------|----------------|
| **Review Effort Modes** | Four tiers – **Fast**, **Balanced** (default), **Deep**, **Auto**. | Provides a spectrum from a single light‑model pass to multiple heavyweight passes, or even skipping the review for trivial generated files. |
| **Auto Mode** | Dynamically picks one of the other tiers (or Skip) based on risk. | Enables adaptive allocation of AI effort per PR. |
| **Hunk Count** | Number of contiguous change blocks in a diff. | More hunks → higher dispersion → higher cognitive load → stronger review needed. It outperforms raw line count as a risk indicator. |
| **Guardrails** | Deterministic rules that limit the router’s decisions (e.g., Deep tier only after meeting minimum line‑ and hunk‑ thresholds; never downgrade when the model is uncertain). | Prevents over‑ or under‑reviewing and ensures safety when the classifier fails. |
| **Cost‑Quality Objective** | Maximizes **F1 – λ·cost** rather than raw F1. | Guarantees that added expense is justified by measurable quality gains. |
| **Failure‑Safe Routing** | If the classifier errors or times out, the system falls back to the Balanced tier instead of aborting. | Guarantees that every PR receives at least a baseline review. |

### Practical Applications  

1. **Cost Reduction** – Large mechanical changes (e.g., lock‑file updates, bulk renames) are routed to **Fast** or **Skip**, saving credits without sacrificing safety.  
2. **Risk‑Focused Scrutiny** – Small but critical edits (e.g., payment‑path logic) generate many hunks; the router upgrades them to **Deep**, catching defects that a single pass would miss.  
3. **Latency Improvement** – Fewer model calls for low‑risk PRs mean faster feedback, keeping developers in the “flow” state.  
4. **Scalable Review Pipeline** – Teams can handle a higher PR volume without expanding human reviewer capacity, as the router automatically throttles AI spend where it adds little value.  
5. **Auditability** – Guardrails and deterministic thresholds make routing decisions explainable, supporting governance and compliance audits.  

### Implementation Sketch  

```mermaid
flowchart TD
    A[Receive PR diff] --> B[Lightweight classifier]
    B --> C{Guardrail checks}
    C -->|Pass| D[Select Tier (Fast/Balanced/Deep/Skip)]
    C -->|Fail| E[Fallback to Balanced]
    D --> F[Run selected review passes]
    E --> F
```

The classifier extracts semantic cues (logic changes, security‑related keywords) and counts hunks. Guardrails enforce minimum‑size thresholds for Deep and prohibit downgrades when uncertainty is high.
