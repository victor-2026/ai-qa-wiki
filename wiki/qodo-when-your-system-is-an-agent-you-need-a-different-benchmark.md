# Qodo: When Your System Is an Agent, You Need a Different Benchmark  

**Date:** 23 Sept 2026 **Source:** <https://www.qodo.ai/blog/when-your-system-is-an-agent-you-need-a-different-benchmark/>

---

## Summary  
Qodo’s code‑review product migrated from a single‑LLM prompt that emitted a YAML list of suggestions to a **Mixture‑of‑Agents (MoA)** pipeline. The old scalar benchmark—one command in, one score out—could no longer capture the nuanced behavior of a multi‑agent system. To keep measuring quality, Qodo built a new benchmarking framework that (1) creates **synthetic PRs** with known defects, and (2) evaluates findings with an **LLM‑as‑Judge ensemble**. The result is a reproducible, cost‑effective feedback loop that supports precision/recall reporting, root‑cause tracing, and rapid iteration on agent components.

---

## Key Concepts  

### 1. From Prompt to System  
| Prompt‑only | MoA (Mixture of Agents) |
|------------|--------------------------|
| One LLM call → YAML list | Multiple specialized agents (Context, Issue, Compliance) with routing, tool calls, and shared state |
| Deterministic output (temp = 0) | Non‑deterministic due to branching, external tools, and dynamic context |
| Single scalar score | Structured findings with provenance, requiring precision/recall metrics |

### 2. Why the Original Benchmark Failed  
* **Determinism loss** – string‑level matching became meaningless.  
* **Changed output format** – need to compare *findings* (agent, rule, location) rather than flat lists.  
* **Multiple findings per PR** – a single aggregated score hides precision/recall trade‑offs.  
* **Ground‑truth fuzziness** – real PRs don’t guarantee known bugs; semantic similarity matters.  
* **Cost explosion** – ensemble judging across many PRs and ablations is far pricier than a single judge call.

### 3. Synthetic PRs  
1. **Start** with a real merged PR.  
2. **Cherry‑pick** it onto a fresh branch.  
3. **Inject** a controlled defect:  
   * *Compliance* – rule violation matching the repo’s policy.  
   * *Issues* – functional bugs (logic error, race condition, resource leak, etc.).  
4. Produce a **CLEAN / CORRUPTED pair** that isolates the defect.  
5. Keep each repo’s injections isolated in a dedicated benchmark organization.

### 4. LLM‑as‑Judge with Ensemble Voting  
* **Holistic mode** – judges compare raw findings against ground truth (file, line, description).  
* **Pairwise mode** – judges compare two systems side‑by‑side for regression testing.  
* **Ensemble** – three providers (OpenAI, Anthropic, Gemini) run in parallel; scores are averaged and standard deviations reported to surface disagreement.  
* **Optimisations** – early‑exit for empty‑case inputs saves ~30 % of LLM calls.

### 5. Benchmarking Flywheel  
* **CI‑driven** – a single `workflow_dispatch` trigger lets engineers toggle agents, adjust synthetic‑bug density, or swap judges.  
* **Run → Inspect → Diagnose → Fix → Re‑run** creates a continuous improvement loop, turning benchmark data into actionable debugging information (e.g., “Compliance agent missed rule X in repo Y”).

## Practical Applications  

| Use‑case | How the Benchmark Helps |
|----------|--------------------------|
| **Product QA** | Quantifies precision/recall for each agent, exposing regressions before release. |
| **Model Selection** | Pairwise LLM‑as‑Judge lets teams compare new model versions or provider swaps with statistical confidence. |
| **Compliance Auditing** | Synthetic rule violations guarantee coverage of organization‑specific standards. |
| **Cost Management** | Ensemble voting reduces provider bias while early‑exit logic keeps evaluation spend predictable. |
| **Debugging** | Provenance (agent + rule + location) lets engineers pinpoint which stage produced a false positive/negative. |
| **Research & R&D** | Controlled synthetic PRs provide a reproducible testbed for novel agents, tool integrations, or routing strategies. |

---

### How to Adopt  
1. **Clone** Qodo’s benchmark repo and configure the benchmark organization.  
2. **Define** the set of rule‑violations and bug types relevant to your codebase.  
3. **Run** the CI workflow, selecting either holistic or pairwise judging.  
4. **Consume** the JSON report: precision, recall, per‑agent hit‑rates, and judge variance.  
5. **Iterate** on agent prompts, tool wrappers, or routing logic, then repeat.
