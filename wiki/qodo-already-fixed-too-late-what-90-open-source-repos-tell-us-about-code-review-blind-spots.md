## Qodo: Already Fixed, Too Late – What 90 Open‑Source Repos Reveal About Code‑Review Blind Spots  

**Date:** 2026‑09‑23 | **Source:** [Qodo blog](https://www.qodo.ai/blog/already-fixed-too-late-what-90-open-source-repos-tell-us-about-code-review-blind-spots/)  

### Summary  
A systematic analysis of 90 popular open‑source projects (spanning 11 languages) shows that code‑review, even when assisted by AI tools, routinely lets subtle defects slip through. By pairing each defect‑introducing pull request (PR) with the later PR that fixed it, the study identified **1,258** “already‑fixed‑too‑late” bugs. The median time to discovery was **16 days** (mean = 46 days). The findings expose a structural blind spot: reviewers see a diff, but lack the broader runtime context needed to spot logic errors, race conditions, and edge‑case regressions.  

### Key Concepts  

| Concept | What the Study Shows |
|---------|----------------------|
| **Blind‑spot definition** | Errors that survive a human + AI review because the review isolates the change from the full codebase and execution state. |
| **Dataset breadth** | 90 actively maintained repos (Django, Angular, VS Code, Terraform, etc.) covering Python, TypeScript, Go, Rust, Java, Ruby, PHP, C/C++, Swift. |
| **Defect‑fix pairing** | Only bugs that were later corrected by a separate PR were counted, guaranteeing the issue was real and not a false positive. |
| **Time‑to‑fix distribution** | 29 % ≤ 1 week, 32 % 1‑4 weeks, 21 % 1‑3 months, 13 % 3‑6 months, 5 % > 6 months. Longer‑lived bugs tended to be race conditions or hidden‑state errors. |
| **Severity & density** | 71 % of the examined repos scored **D/F** on a severity‑density metric, indicating many high‑impact findings per PR. |
| **Tool coverage** | Even projects already using AI‑powered reviewers exhibited the same blind spots, confirming the issue is not tool‑specific but inherent to diff‑based review. |
| **Unfixed bugs** | Hundreds of validated defects remain in production, underscoring that the reported 1,258 is a lower bound. |

### Practical Applications  

1. **Augment Diff Review with Whole‑Program Analysis**  
   - Integrate static and dynamic analyses that evaluate the change in the context of the entire codebase (e.g., data‑flow, type‑state, and concurrency models).  
   - Use AI to surface “what‑if” scenarios that the diff alone cannot reveal.

2. **Post‑Merge Guardrails**  
   - Deploy automated canary or shadow testing that runs newly merged code against a broader set of integration tests and real‑world traffic patterns.  
   - Flag regressions early, before users encounter them.

3. **Prioritise High‑Risk PRs**  
   - Leverage the severity‑density scores to identify repositories or modules where review blind spots are most acute.  
   - Allocate additional reviewer bandwidth or stricter gating (e.g., required performance benchmarks) for those areas.

4. **Feedback Loop to Reviewers**  
   - When a later fix matches a previously missed finding, automatically annotate the original PR with the missed pattern.  
   - Over time, this builds reviewer intuition about recurring blind‑spot categories.

5. **Metric‑Driven Process Improvement**  
   - Track median time‑to‑fix and distribution per team; aim to shrink the median below the current 16 days.  
   - Use the “D/F” scoring as a health indicator and set targets for improvement.

6. **Community Collaboration**  
   - Open‑source maintainers can submit the identified unfixed bugs to Qodo’s community channel for triage, turning the study into a collaborative bug‑bounty pipeline.

### Take‑away  
Code review remains a cornerstone of software quality, but the study proves it cannot alone guarantee defect‑free releases. The blind spot stems from limited contextual visibility, not reviewer negligence. Teams that complement traditional review with whole‑program AI analysis, post‑merge testing, and systematic feedback will close the gap and reduce the costly “already fixed, too late” cycle.
