## AI Agent Control Logic with Pattern Matching  
*Haim Michael – AI Agents Conference, 27 Apr 2026*  

### Summary  
Haim Michael presented a pragmatic approach for building a deterministic control layer on top of inherently stochastic AI agents. By leveraging Java’s sealed‑type pattern matching (as used in LangChain4j AiServices), the orchestrator can express routing, retries, parallel‑execution and verdict handling as exhaustive, compiler‑checked branches. The talk distilled four reusable patterns—pipeline orchestration, enum‑bridge routing, bounded retry loops with score‑gated feedback, and fan‑out/fan‑in judging—and highlighted how these patterns improve predictability, testability, and maintainability of agent‑centric systems.

### Key Concepts  

| Concept | What it is | Why it matters |
|---------|------------|----------------|
| **Sealed‑type messages** | A closed hierarchy of `AgentMessage` (e.g., `PlanRequest`, `CodeRequest`, `ReviewRequest`, `FinalResult`). | Guarantees that every possible agent output is handled; the compiler flags missing cases. |
| **Pattern‑matching orchestrator** | `switch`/`case` on sealed messages to decide the next step, with explicit `try/catch` per delegation. | Removes fragile `if‑else` chains and makes the control flow visible in the source. |
| **Enum‑bridge for deserialization** | Convert a non‑serializable sealed interface into an enum (`TaskClassification`) before sending it to LangChain4j. | Works around a current limitation of the library while preserving type safety downstream. |
| **Bounded retry with guarded patterns** | Loop up to `MAX_ATTEMPTS`; coder → reviewer returns either `Approved(score)` or `Rejected(feedback)`. A guard `when a.score() > 7` creates a fast‑track path; otherwise the loop continues with enriched feedback. | Encodes a “verdict gate” that limits cost, enforces quality thresholds, and produces a clear give‑up signal. |
| **Parallel‑agent judging** | Two solvers run on virtual threads (`StructuredTaskScope`); a `JudgeAgent` selects the winner via a sealed `JudgeVerdict`. | Isolates parallelism from decision logic, enabling deterministic testing of the selection criteria. |
| **Package‑visible orchestrators** | Orchestrator classes are exposed only within the module, allowing unit tests with mocked agents. | Aligns with the team’s requirement for fully testable control‑plane components. |

### Practical Applications  

1. **Verdict‑Gate Loops for QA** – The retry pattern can be adopted for any “review‑approve” workflow (e.g., code review, content moderation). By parameterising the score threshold per risk tier, the same skeleton enforces different safety levels without code duplication.  

2. **Typed Verdict Types** – Sealed result types such as `AgentResult` (Answer | Clarification | Error) or `JudgeVerdict` (PickedA | PickedB) provide a strongly‑typed contract for downstream components like evidence‑artifact generators or audit logs.  

3. **Deterministic Routing** – Replacing ad‑hoc `if` statements with enum‑bridge routing yields a single source of truth for task classification, simplifying future extensions (e.g., adding a `TranslateTask`).  

4. **Parallel Evaluation Harnesses** – The fan‑out/fan‑in pattern fits well with “judge‑agreement” mechanisms where multiple agents propose solutions and a deterministic selector resolves conflicts, mirroring the single‑judge design used in the Qodo examiner.  

5. **Testability Blueprint** – Making orchestrators package‑visible and injecting mock agents mirrors the testing strategy required for the CIGE guardrails and AgentSpec runtime enforcement layers.  

6. **Engineering Constraints Awareness** – The enum‑bridge workaround reminds designers to account for serialization limits of third‑party libraries early in the architecture.
