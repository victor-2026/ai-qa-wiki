## Amazon Science – Formally Verified EC2 Isolation Engine  

**Date:** 10 Jun 2026  

### Summary  
AWS announced the general‑availability of the M9g/M9gd EC2 instances, the first to run on the Graviton5 CPU and to incorporate the **Nitro Isolation Engine**. This component, extracted from the broader Nitro Hypervisor, is a minimal *separation kernel* whose sole responsibility is to enforce strict isolation between virtual machines (VMs). Using the Isabelle/HOL proof assistant, Amazon produced a machine‑checked model and proof of correctness spanning 330 k lines of formal mathematics—making it the first formally verified hypervisor component deployed in a production cloud. The engine is implemented in a restricted subset of Rust (μRust) and verified for confidentiality, integrity, functional correctness, absence of runtime errors, and memory safety.

### Key Concepts  

| Concept | What it means | Why it matters |
|---------|---------------|----------------|
| **Separation kernel** | A tiny OS layer that enforces isolation without handling scheduling, resource allocation, or policy decisions. | Simpler code base → feasible formal verification. |
| **Nitro Isolation Engine** | The isolated kernel inside the Nitro Hypervisor that checks every request that touches guest state. | Guarantees that VM‑to‑VM leakage or interference cannot occur. |
| **Formal specification** | Precise, mathematical description of expected behavior (pre‑/post‑conditions) expressed in Isabelle/HOL. | Provides an unambiguous contract for the implementation. |
| **Proof of correctness** | Machine‑checked theorems showing the implementation meets its specification. | Gives mathematical assurance of security properties. |
| **μRust** | A deliberately limited fragment of Rust that excludes traits, dynamic dispatch, etc., making it amenable to formal reasoning. | Enables a shallow embedding in Isabelle/HOL while retaining enough expressiveness for the engine. |
| **Separation Logic** | Logic for reasoning about pointer‑rich programs; used to write contracts for μRust functions. | Allows concise, compositional specifications of memory safety. |
| **Weakest‑precondition calculus** | Technique that derives the minimal pre‑condition needed for a post‑condition to hold after executing code. | Drives the automated proof obligations for functional verification. |
| **Confidentiality & Integrity properties** | Formalized as transition‑relation invariants ensuring no unauthorized information flow and that state changes are legitimate. | Directly addresses cloud‑tenant security guarantees. |

### Practical Applications  

1. **Stronger tenant isolation in public clouds** – Customers of M9g/M9gd instances receive mathematically proven guarantees that their VMs cannot read or corrupt each other’s memory, even in the presence of buggy hypervisor code.  
2. **Audit‑ready compliance** – The verified engine supplies a concrete artifact that regulators and security auditors can inspect, simplifying certifications such as FedRAMP, PCI‑DSS, or ISO 27001.  
3. **Foundation for verified cloud services** – The verification methodology (μRust + AutoCorrode) can be reused to certify other critical components (e.g., device‑pass‑through, live migration).  
4. **Improved reliability** – Proofs of “absence of runtime errors” eliminate panics caused by `unwrap` on `None`, reducing unexpected instance crashes.  
5. **Research and education** – The open‑sourced AutoCorrode library and the Isabelle/HOL model serve as teaching material for formal methods courses and as a baseline for future verification projects.
