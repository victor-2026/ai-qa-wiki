## Are My Tests Actually Testing Anything? – 5 Quick Checks  

**Source:** https://getautonoma.com/blog/how-to-tell-if-tests-are-testing-anything  
**Author:** Tom Piaggio, Co‑Founder, Autonoma (June 2026)

---

### Summary  
A test suite that never fails when the production code is deliberately broken is “theater” – it gives a false sense of safety.  
The fastest way to expose such hollow tests is to *tamper with the code* and watch the suite’s reaction. Five lightweight checks (≈10 min, no special tools) let you decide whether your tests verify real behavior or merely confirm that the code runs.

---

### Key Concepts  

| # | Check | What you do | Success Indicator | What failure reveals |
|---|-------|-------------|-------------------|----------------------|
| 1 | **Comment‑out a line** | Remove a line of business logic. | At least one test turns red. | The line is exercised but never asserted. |
| 2 | **Introduce a bug** | Flip a comparison, invert a boolean, change a return value. | A test catches the regression. | The test is tautological – it expects whatever the broken function now returns. |
| 3 | **Inspect assertions** | Ask whether each `expect`/`assert` checks an observable outcome (API response, UI, return value) or an internal detail (private variable, mock call count). | All assertions target external behavior. | Tests are tied to implementation; they validate the mock rather than the system. |
| 4 | **Mutation survivability** | Run a mutation engine (Stryker, PIT, mutmut). | Mutation score > 70 % on critical paths. | High line coverage with a low mutation score signals gaps in verification. |
| 5 | **Delete‑and‑measure** | Remove a single test, rerun coverage. | Coverage drop corresponds to a genuine behavioral gap. | Coverage falls only a few points while the behavior remains unchecked – the test was superficial. |

---

### Practical Applications  

| Context | How the checks are used | Outcome |
|---------|------------------------|---------|
| **CI quality gates** | Automate checks 3 & 5 as pre‑commit lint rules. | Prevents merging of tests that only boost line‑coverage metrics. |
| **Fault‑injection pipelines** (e.g., Buzzhive) | Automate checks 1 & 2; every injected fault must cause a failure. | Guarantees that the suite reacts to real defects. |
| **AI‑generated test suites** | Apply checks 2 & 3 to catch “self‑fulfilling” tests where the model writes matching expectations. | Stops the model from cementing bugs as “expected” behavior. |
| **Regression‑risk assessment** | Run mutation testing (check 4) on critical modules before release. | Highlights untested edge cases despite high coverage numbers. |
| **Test‑suite pruning** | Periodically delete a test (check 5) to see if any functional guarantee disappears. | Identifies and removes dead weight, keeping the suite lean. |

---

### Related Topics  

- **Mutation Testing** – measuring how many artificial bugs are caught by the suite.  
- **Behavior‑Driven Development (BDD)** – emphasizes observable outcomes over implementation details.  
- **Fault Injection** – deliberately corrupting a system to verify resilience.  
- **AI‑assisted Test Generation** – benefits from structural separation (planner, executor, reviewer) to avoid “self‑validating” tests.  
- **Coverage Metrics** – line vs. branch vs. mutation scores; why line coverage alone is misleading.  

---

By routinely performing these five checks, teams can turn a green‑only test run into a reliable safety net that truly protects against regressions, regardless of whether the tests were written by humans or AI.
