## Failure Mode and Effects Analysis (FMEA) в QA‑тестировании  

### Краткое содержание  
FMEA — проактивный метод, заимствованный из инженерии и медицины, который позволяет предвидеть и оценить потенциальные отказы системы до её ввода в эксплуатацию. В контексте QA команда использует искусственный интеллект для автоматического извлечения типовых дефектов из истории багов, формирования перечня возможных отказов и проверки новых задач на соответствие этим сценариям. Такой «живой» список постоянно пополняется, что повышает покрытие тестов и снижает риск повторных ошибок.

### Ключевые понятия  

| Понятие | Описание |
|---------|----------|
| **Failure Mode** | Способ, которым конкретная функция может выйти из строя (например, неверная валидация входных данных). |
| **Effect** | Последствия отказа для пользователя, бизнеса или других компонентов системы. |
| **Severity (S)** | Оценка тяжести последствий (обычно 1‑10). |
| **Occurrence (O)** | Вероятность возникновения конкретного отказа (1‑10). |
| **Detection (D)** | Насколько легко обнаружить отказ до релиза (1‑10). |
| **RPN (Risk Priority Number)** | Произведение S × O × D; используется для приоритизации исправлений. |
| **Action Priority (AP)** | Альтернатива RPN по стандарту AIAG‑VDA (2019): классификация High/Medium/Low на основе комбинаций S/O/D, а не простого умножения. |
| **DFMEA** | Design FMEA — анализ отказов на этапе проектирования (материалы, геометрия, допуски, интерфейсы). |
| **PFMEA** | Process FMEA — анализ отказов производственных процессов (человеческий фактор, методы, материалы, оборудование). |
| **FMECA** | Расширение FMEA с Criticality Analysis — количественная оценка критичности каждого отказа. |
| **AI‑поддерживаемый FMEA** | Автоматическое построение и обновление списка отказов на основе анализа реальных баг‑репортов. |

### История метода
FMEA разработан в 1940‑х годах для военных стандартов США (MIL‑STD‑1629), впоследствии принят NASA и автомобильной промышленностью. Современный стандарт — AIAG‑VDA FMEA Handbook (1‑е издание, 2019), объединивший американский AIAG и немецкий VDA подходы. В 2026 году метод переживает второе рождение благодаря AI‑автоматизации: появились инструменты, генерирующие FMEA из технической документации за минуты, а не недели.

### Типы FMEA

| Тип | Объект анализа | Примеры failure modes |
|-----|---------------|----------------------|
| **DFMEA** (Design) | Проектируемый продукт | Поломка материала, неправильные допуски, отказ интерфейсов |
| **PFMEA** (Process) | Производственный/тестовый процесс | Ошибка оператора, сбой оборудования, неверные данные |
| **SFMEA** (System) | Взаимодействие подсистем | Потеря связи, race condition, каскадный отказ |
| **FFMEA** (Functional) | Функции системы | Неверный вывод, отсутствие обработки краевых случаев |

### 7‑шаговая методология AIAG‑VDA

1. **Structure Analysis** — декомпозиция системы/процесса на элементы
2. **Function Analysis** — описание функций каждого элемента
3. **Failure Analysis** — для каждой функции: Failure Effects → Failure Mode → Failure Cause
4. **Risk Analysis** — оценка S (Severity), O (Occurrence), D (Detection) и приоритет AP
5. **Optimization** — корректирующие действия с ответственными и сроками
6. **Results Documentation** — фиксация результатов переоценки риска
7. **Continuous Improvement** — регулярный пересмотр на основе новых данных

### Практическое применение в AI‑стартапе  

1. **Сбор паттернов из истории багов**  
   - AI‑модель сканирует репозитории и тикет‑системы, выделяя повторяющиеся проблемы (валидация внешних данных, авторизация, изоляция клиентских данных, таймауты внешних сервисов).  
   - Для каждого паттерна фиксируются условия возникновения, требуемые профилактические меры и ссылка на конкретный инцидент.  

2. **Создание динамического реестра отказов**  
   - Полученный список сохраняется в базе, где каждому пункту присвоены оценки S, O, D и вычисленный RPN.  
   - При появлении новых багов реестр автоматически пополняется, а оценки пересчитываются.  

3. **Проверка новых задач разработки**  
   - При создании пользовательской истории AI сравнивает её условия с реестром.  
   - Если совпадения обнаружены, а необходимые проверки не указаны, система помечает задачу как «упущение» и предлагает добавить соответствующие тест‑кейсы.  

4. **Непрерывное улучшение**  
   - После релиза результаты тестов и новые баги снова анализируются, что позволяет своевременно вводить новые Failure Modes.  

**Преимущества**  
- Сокращение количества повторяющихся дефектов.  
- Повышение объективности оценки риска (RPN/AP).  
- Автоматизация рутинных проверок, освобождающая время QA‑инженеров.
