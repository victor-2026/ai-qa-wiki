# Database Design (Relational & Non-Relational) for Beginners

## What It Is
Проектирование БД — это решение, **где и как хранить данные**, чтобы приклады легко читали/писали их, не ломали целостность и не тормозили. Две большие семьи: **реляционные** (SQL: PostgreSQL, MySQL, SQL Server) и **нереляционные** (NoSQL: MongoDB, Redis, Cassandra, DynamoDB). Выбор зависит от формы данных и нагрузки.

Для QA навык нужен: (1) писать корректные проверки данных (что пишется в БД, в правильном ли виде), (2) понимать схему для тест-сеапов, (3) проверять миграции и целостность.

## Реляционные (SQL) — основа
Данные в **таблицах** с фиксированной схемой. Связи через ключи. Пример — PostgreSQL:

```sql
-- таблица пользователей
CREATE TABLE users (
    id         SERIAL PRIMARY KEY,
    email      TEXT NOT NULL UNIQUE,
    created_at TIMESTAMP DEFAULT now()
);

-- таблица заказов (связь многие к одному: заказ → пользователь)
CREATE TABLE orders (
    id        SERIAL PRIMARY KEY,
    user_id   INT REFERENCES users(id),
    total     NUMERIC(10,2),
    status    TEXT DEFAULT 'new'
);
```

Ключевые понятия: `PRIMARY KEY` (уникальный идентификатор строки), `FOREIGN KEY` (ссылка на другую таблицу — целостность), `NOT NULL` / `UNIQUE` / `DEFAULT` — ограничения, которые защищают от битых данных. Это и есть «дизайн»: не просто таблицы в коде, а именно правила целостности.

Пример запроса: сколько заказов на пользователя:
```sql
SELECT u.email, COUNT(o.id) AS orders
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.email;
```

## Нереляционные (NoSQL) — когда схема гибкая
Вместо фиксированных таблиц — **документы** (JSON-подобные), **ключач-значения**, **графы**. MongoDB — самый известный документный пример:

```js
// один документ = один пользователь со своими заказами внутри
db.users.insertOne({
  email: "alice@example.com",
  orders: [{ id: 1, total: 150.5, status: "paid" }]
})
```

Плюсы: гибкая схема (поля могут отличаться у разных документов), легко масштабировать. Минусы: за слабую типизацию платишь чтением — тесты на наличие/типы полей критически важны.

## Реляционное ИЛИ нереляционное — правило выбора
| Критерий | SQL (PostgreSQL/SQL Server) | NoSQL (MongoDB) |
|---|---|---|
| Схема/структура | фиксированная | гибкая |
| Связи (пользователь↔заказ) | внешние ключи, JOIN | вложенные документы / ссылки |
| Целостность | сильные констрейны (нельзя вставить битое) | сам следишь |
| Масштаб/нагрузка | вертикаль + партиции | горизонтальная шардинг |
| Подходит | финтех, транзакции, отчёты | логи, каталоги, профили, high-volume |

Важно: выбор не «новое всегда лучше». Одно и то же приложение может комбинировать: PostgreSQL — деньги и транзакции, MongoDB — каталог и заметки.

## Что проверить как QA (по БД)
1. **Констрейня ловят?** Вставить `email: NULL`, `price: -5`, дубликат ключа — должно 400/500 или SQL-ошибка.
2. **Каскады.** Удаление пользователя обнуляет/удаляет его заказы? Потери данных без каскада = битый FK.
3. **Миграции.** Схема v1→v2 не ломает старые строки (данные не теряются).
4. **Типы.** Числа не превращаются в строки, даты не сдвигаются, NULL vs "" различаются.
5. **Транзакции.** Частичный успех (половина-записи в случае ошибки) — признак отсутствия транзакции.

Пример теста на PostgreSQL через pytest:
```python
def test_delete_user_removes_orders(pool):
    with pool.connection() as conn:
        conn.execute("DELETE FROM users WHERE id=42")
        rows = conn.execute(
            "SELECT count(*) FROM orders WHERE user_id=42").fetchone()[0]
    assert rows == 0
```

## TL;DR Для резюме
- Реляционные: PostgreSQL, SQL Server — схемы, ключи (PK/FK), ограничения, JOIN, транзакции, миграции.
- Нереляционные: MongoDB — документы, гибкая схема, вложенные структуры.
- Выбор: по форме данных/связям/нагрузке; умею проектировать и комбинировать.
- QA-плюс: проверки целостности, каскадов, миграций, типов; test-db isolation/cleanup.
