## Engineering Standards for AI‑Driven Development  
*Based on Rod Morison’s **rmorison/engineering-standards** and EveryInc’s **compound‑engineering‑plugin** (MIT‑licensed)*  

### Summary  
These standards describe a lightweight, AI‑first way of building software where the large language model (LLM) is treated as a permanent team member. A **six‑layer architecture** separates concerns—from persistent session rules to deterministic hooks—while the **Compound Engineering** plugin supplies concrete implementations for the middle layers. Development follows a **spec‑driven, iterative loop** (Intent → Spec → Plan → Execute → Validate) that keeps the codebase continuously deployable and the AI’s context minimal and relevant.

### Key Concepts  

| Concept | What it means | Why it matters |
|---------|---------------|----------------|
| **Six‑Layer AI Architecture** | 1️⃣ Rules (session persistence) 2️⃣ Workflow Skills (composable orchestrators) 3️⃣ Persona Agents (expertise slices) 4️⃣ References (progressive context) 5️⃣ Compound/Learnings (institutional memory) 6️⃣ Hooks (deterministic enforcement) | Provides a vendor‑neutral scaffold; layers 2‑5 are realized by Compound, keeping the core repo portable. |
| **Spec‑Driven Development** | Specs are written before any code, stored in `docs/`, and serve as contracts for testing and AI prompts. | Gives the LLM a clear, bounded context, reduces hallucinations, and enables automated validation. |
| **Compound Loop** | 1️⃣ Brainstorm → 2️⃣ Plan → 3️⃣ Work → 4️⃣ Simplify → 5️⃣ Code‑Review → 6️⃣ Compound → repeat. | Emphasises planning & review (≈ 80 % of effort) and captures every learning back into the wiki‑like `docs/solutions/`. |
| **AI‑Native GitHub Flow** | Main branch always deployable, issue‑based feature branches, conventional commits, semantic versioning. | Aligns with CI/CD best practices while allowing AI‑generated PRs to be gated by deterministic hooks. |
| **Compound Packs** | Collections of prescriptive rule files (local or remote) that ground planning and enforce compliance during review. | Guarantees that every run cites its source rule, turning ad‑hoc knowledge into reusable policy. |
| **Deterministic Hooks** | Non‑AI checks (linters, security policies) that run with zero AI context cost. | Prevents the AI from bypassing essential safety nets. |

### Practical Applications  

| Situation | How to apply the standards |
|-----------|----------------------------|
| **Startup or solo project** | Adopt the six‑layer scaffold, use the provided `templates/.claude/` folders, and run the `lfg` autonomous pipeline for end‑to‑end PR generation. |
| **Cross‑model team** | Deploy the 14 agent hosts (Claude Code, Cursor, Codex, etc.) via the `opencode.json` plugin array; each host can own a layer (e.g., Persona Agents). |
| **Institutional memory building** | After each PR, run `ce‑compound` to write a learning into `docs/solutions/`. Future `ce‑plan` runs automatically surface relevant learnings (e.g., env‑var traps). |
| **Safety‑critical component** | Keep Layers 1 (rules) and 6 (hooks) under strict version control; enforce them with ADR‑0001 and CI checks before any AI‑generated code merges. |
| **Continuous QA** | Treat the spec as a BDD/Gherkin contract; mutation testing reads the spec as an oracle, while `ce‑code‑review` validates implementation against the plan. |

By keeping specs concise, loading only the needed context, and feeding every outcome back into a searchable knowledge base, teams can scale AI assistance without accruing technical debt or hidden brittleness.
