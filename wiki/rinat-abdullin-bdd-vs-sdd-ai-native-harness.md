## SDD vs BDD – AI‑Native Harness  

**Источник:** Rinat Abdullin (@llm_under_hood), 2026‑06  

---  

### 📄 Краткое содержание  
Spec‑Driven Development (SDD) часто приводит к «мёртвым» спецификациям: после написания кода они больше не проверяются, а аудит их соответствия требует ручных усилий. Behaviour‑Driven Development (BDD), созданный два десятка лет назад, решает эту проблему, делая требования исполняемыми тестами. При интеграции с LLM‑агентами BDD превращается в **AI‑Native Harness** – автоматический механизм, который генерирует, проверяет и поддерживает синхронность требований и кода без человеческого вмешательства.  

---  

## Ключевые понятия  

| Понятие | Описание | Роль в AI‑Native Harness |
|--------|----------|--------------------------|
| **SDD (Spec‑Driven Development)** | Спецификации пишутся заранее, но потом остаются «документом», не проверяемым автоматически. | Показательный пример проблемы, которую решает BDD. |
| **BDD (Behaviour‑Driven Development)** | Методология, описывающая поведение системы через читаемые сценарии (Given‑When‑Then). | Основная «обёртка» для автоматических проверок. |
| **Given‑When‑Then** | Формат сценариев: предусловие → действие → ожидаемый результат. | Делает требования понятными как для бизнеса, так и для кода. |
| **AI‑Native Harness** | Набор LLM‑агентов, которые (1) трансформируют высокоуровневые требования в BDD‑сценарии, (2) генерируют/корректируют код, (3) запускают тесты многократно за сессию. | Позволяет выполнять «живую» валидацию требований. |
| **Event‑driven specs** | Спецификации, построенные вокруг событий вместо Gherkin‑сценариев. | Альтернатива для проектов с >10 k спецификаций; вопрос вкуса. |
| **Harness engineering** | Инженерия тестовых «охватов», обеспечивающих автоматический запуск и мониторинг. | Третий компонент экосистемы BDD + AI. |

## Практические применения  

1. **Автоматическое поддержание согласованности**  
   - LLM‑агент разбивает бизнес‑требования на отдельные BDD‑сценарии.  
   - При изменении требования агент обновляет соответствующие сценарии и генерирует/модифицирует код.  

2. **Масштабируемый регрессионный тестинг**  
   - Один сценарий может быть выполнен сотни раз в рамках одной CI‑сессии, выявляя даже редкие отклонения.  

3. **Zero‑maintenance спецификации**  
   - Ошибки в сценариях сразу приводят к падению сборки, устраняя «мёртвый» груз документации.  

4. **Поддержка больших проектов**  
   - Для систем с десятками тысяч спецификаций предпочтительнее event‑driven подход, позволяющий хранить требования в виде потоков событий, а не линейных Gherkin‑файлов.  

5. **Обучение и онбординг**  
   - Читаемые сценарии служат живой документацией, ускоряя ввод новых членов команды.

## Связанные темы  

- **Gherkin** – DSL для описания BDD‑сценариев; часто используется с Cucumber, Behave и др.  
- **Cucumber / JBehave / RSpec / Behave** – фреймворки‑парсеры, превращающие сценарии в end‑to‑end тесты.  
- **LLM‑driven code generation** – генерация кода на основе естественного языка, ключевой элемент AI‑Native Harness.  
- **Continuous Integration / Continuous Testing** – интеграция BDD‑harness в пайплайн CI для мгновенной обратной связи.  
- **Event‑sourcing** – архитектурный стиль, совместимый с event‑driven specs.

### Заключение  
Перевод SDD в BDD, усиленный LLM‑агентами, превращает статичные требования в живой, самопроверяемый набор тестов. Это устраняет разрыв между бизнес‑целями и реализацией, делает процесс масштабируемым и снижает технический долг, особенно в крупных проектах, где предпочтительнее event‑driven спецификации.
