## CSV Validation Protocols – IQ, OQ, PQ  

**Summary**  
Computer System Validation (CSV) guarantees that a computerized system consistently delivers its intended function while meeting regulatory demands (21 CFR Part 11, EU Annex 11, GxP).  The core CSV mantra – *“If it isn’t documented, it didn’t happen.”* – drives a fully traceable, auditable lifecycle.  GAMP 5 provides a risk‑based framework that maps the lifecycle to three qualification phases: **Installation Qualification (IQ)**, **Operational Qualification (OQ)**, and **Performance Qualification (PQ)**.  The depth of each phase depends on the system’s GAMP category and its impact on patient safety or data integrity.

---

### Validation Lifecycle (GAMP 5)

```
Concept → Requirements → Design → Build → Test → Release → Operation → Retirement
                                          ↓
                                     IQ / OQ / PQ
```

| GAMP Category | Typical System | Required Qualification |
|---------------|----------------|------------------------|
| 1 – Infrastructure | OS, DB, network | Minimal (recorded) |
| 3 – Standard off‑the‑shelf | Excel, Jira | OQ only |
| 4 – Configured product | LIMS, ERP | IQ + OQ + PQ |
| 5 – Custom application | Bio‑informatics pipeline | Full IQ/OQ/PQ + design specs |

---

### Installation Qualification (IQ)

**Goal:** Verify that the system is installed exactly as the vendor specifies.  

Key checks: hardware model, software version, environment conditions (temperature, power), security settings, and completeness of manuals.  

**Typical IQ template**  
1. System identification (name, version, serial)  
2. Installation checklist (component → verified by → date)  
3. Environment verification (temp, humidity, UPS)  
4. Software version validation (checksum, installer log)  
5. Baseline configuration snapshot  
6. Deviations & resolutions  
7. Approvals (4‑eyes principle)  

---

### Operational Qualification (OQ)

**Goal:** Demonstrate that the system performs all functions correctly under normal and boundary conditions.  

Typical OQ activities: functional testing against the User Requirements Specification (URS), boundary‑value testing, error handling, security/access controls, interface validation, and alarm verification.  

**OQ test case example**

| ID | Requirement | Test Step | Expected | Actual | Pass |
|----|-------------|-----------|----------|--------|------|
| OQ‑01 | Authenticate user | Valid credentials | Dashboard loads | Dashboard loaded | ✅ |
| OQ‑02 | Reject invalid login | Wrong password | Error message | “Invalid credentials” | ✅ |
| OQ‑03 | Capture audit trail | Login then view log | Entry with user/time | Entry found | ✅ |

A traceability matrix links each test to its requirement.

---

### Performance Qualification (PQ)

**Goal:** Confirm that the system sustains required performance in the live production environment.  

PQ focuses on end‑to‑end business scenarios, load/stress limits, data‑integrity checks, backup‑restore cycles, and disaster‑recovery procedures.  

**Typical PQ template**  
1. Business process description  
2. Real‑world scenarios (e.g., 7‑day continuous run)  
3. Performance metrics (response time, throughput)  
4. Data integrity verification  
5. Backup/restore validation  
6. Deviations & corrective actions  
7. Approvals

### Validation Documentation Package (Audit Ready)

```
Validation Plan (VP)
├─ URS (User Requirements Spec)
├─ Functional & Design Specs
├─ Risk Assessment
├─ IQ Protocol & Report
├─ OQ Protocol & Report
├─ PQ Protocol & Report
├─ Traceability Matrix
├─ Validation Summary Report (VSR)
├─ SOPs
└─ Training Records
```

The **Validation Summary Report** condenses all activities, lists deviations, and states the final conclusion (“system is validated for production”).

---

### Key Concepts

| Concept | Meaning |
|---------|---------|
| **4‑Eyes Principle** | One person prepares a document; an independent reviewer approves it. |
| **Deviation Handling** | Record → root‑cause → impact assessment → corrective action → re‑test → close. |
| **Change Control** | Any post‑validation change triggers impact assessment, possible re‑qualification, and documentation. |
| **Periodic Review** | Annual (or scheduled) check that the system, SOPs, and training remain valid. |
| **Risk‑Based Validation** | Validation effort matches risk: low‑impact Category 3 may skip IQ/PQ, while Category 5 demands full lifecycle evidence. |
