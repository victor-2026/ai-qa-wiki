# OpenRouter Fusion – Multi‑Model Deliberation  

**Launch:** 12 June 2026 **Status:** Confirmed **Access:** `openrouter/fusion` slug, server‑tool, Fusion plugin, or the no‑code chatroom at `openrouter.ai/fusion`.

---

## Summary  
OpenRouter Fusion is a compound‑AI service that turns a single prompt into a **panel‑based deliberation**. Up to eight models answer in parallel (with web‑search/fetch enabled), a designated judge model analyses the set of replies, and an outer model composes a single, synthesized response. Unlike a router that selects one model, Fusion runs a *mini‑ensemble* and returns the result of a structured comparison, making it ideal for high‑risk QA, testing, and any task where a wrong answer is costly.

---

## Key Concepts  

| Concept | What it means |
|---------|----------------|
| **Panel** | 1‑8 models generate independent completions, each allowed up to 8 tool‑calls (search, fetch, etc.). |
| **Judge** | Receives every panel answer and emits a JSON report containing: <br>• **Consensus** – points most models agree on (high confidence) <br>• **Contradictions** – direct disagreements <br>• **Partial coverage** – topics only some models touched <br>• **Unique insights** – novel ideas from a single model <br>• **Blind spots** – areas no model addressed |
| **Outer model** | Usually the same model that acted as judge; it writes the final answer using the JSON analysis rather than a simple majority vote. |
| **Recursion protection** | A request header (`x-openrouter-fusion-depth`) guarantees only one level of deliberation; panel and judge models cannot invoke Fusion again. |
| **Presets** | *Quality* (default, 3 frontier models + judge, ~4‑5× cost of a solo call) and *Budget* (cheaper mix, ~0.4× cost of a top‑tier solo model). |
| **Cost scaling** | Linear with panel size; each extra model adds one completion cost plus any web‑search fees. No hidden per‑request surcharge. |
| **Escalation layer** | Fusion is intended for selective use—only when the potential impact of an error outweighs the added compute expense. |

## Practical Applications for QA & Testing  

1. **Test‑strategy review** – A panel examines a test plan from security, performance, and maintainability angles; the judge highlights missing coverage.  
2. **Bug triage / root‑cause analysis** – Independent model analyses of logs/screenshots surface consensus findings and flag contradictory hypotheses for human inspection.  
3. **Flaky‑test classification** – Cross‑model agreement helps distinguish environmental failures from code defects, reducing false‑positive alerts.  
4. **Test‑case generation audit** – One model creates test cases, while the panel critiques them for edge‑cases and specification gaps.  
5. **Requirement ambiguity detection** – Divergent interpretations in the panel’s JSON expose ambiguous spec sections that need clarification.  
6. **High‑stakes code review** – For security‑critical changes (e.g., auth, billing, DB migrations), the Quality preset provides an extra safety net.  
7. **Metamorphic‑testing oracle** – When no ground truth exists, the panel’s consensus can serve as a provisional oracle for automated checks.

**Strategy tip:** Adopt the Budget preset for routine checks (it outperforms most solo frontier models at half the cost) and reserve the Quality preset for release sign‑offs or security reviews.

## Related Topics  

- **Compound AI systems** – architectures that combine multiple models with orchestration logic (e.g., tool‑calling agents).  
- **Model routing vs. deliberation** – routers pick a single model per request; deliberation runs several and synthesises a result.  
- **DRACO benchmark** – a suite of deep‑research tasks used to evaluate Fusion; Fusion with Opus 4.8 + Opus 4.8 achieved a 65.5 % score, a 6.7‑point lift over a single run, proving the value of synthesis.  
- **Tool‑calling** – Fusion panels automatically enable `web_search` and `web_fetch`, extending their knowledge beyond the model’s training cut‑off.  
- **Cost‑aware AI orchestration** – techniques for balancing expense and quality by mixing cheap and expensive models within a single request.
