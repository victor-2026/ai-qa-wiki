## Саммари

Harness — программная среда, превращающая языковую модель из функции вида context → response в исполнителя многошаговой работы. Модель дает намерения, харнес — детерминированное исполнение: контекст, инструменты, tool calls, состояние, права, ошибки, возврат результатов. Формула: Agent = Model + Harness + Goal. По мере сближения возможностей моделей качество определяется средой (harness engineering), а вопрос смещается с "какую модель взять?" на "как построить надежную систему исполнения?". Архитектурно: control plane (процесс) отдельно от execution plane (действия), между вероятностным решением и детерминированным side effect — контролируемый контракт.

## Что такое harness

Термин AI harness все чаще встречается в разговорах про AI-агентов. Точного русского эквивалента пока нет, обычно используют английское слово. По смыслу harness — программная среда, которая превращает языковую модель из функции вида context → response в исполнителя, способного выполнять многошаговую работу.

Сама LLM умеет получить контекст и сгенерировать ответ. Она не читает файлы, не запускает Python, не делает SQL-запросы, не вызывает корпоративные API и не хранит состояние процесса, если все это не организовано внешней системой. Harness отвечает именно за этот слой: формирует контекст, предоставляет модели инструменты, выполняет tool calls, хранит состояние, управляет правами, обрабатывает ошибки и возвращает результаты действий обратно модели.

Цикл Model → Tool → Result → Model — центральная часть harness. Вокруг него обычно находятся context management, memory, state, permissions, sandbox, retries, human approval, logging и evaluators, которые позволяют проверить, действительно ли задача выполнена.

Полезно разделять понятия. Model — интеллектуальное ядро. Tools дают возможность воздействовать на внешний мир. Harness организует выполнение и связывает модель, инструменты, данные и ограничения в одну систему. А agent условно:

```
Agent = Model + Harness + Goal
```

## Граница вероятностного и детерминированного

Для проектировщика особенно важно, что harness находится на границе между вероятностной и детерминированной частями информационной системы. Модель может решить, что нужно "создать заказ клиенту", но реальная система требует конкретного вызова API с валидными параметрами, проверкой полномочий, обработкой ошибок и защитой от повторного выполнения.

Модель работает с намерениями, гипотезами и вариантами действий, а корпоративная система — с однозначными командами, схемами данных и правилами выполнения. Harness связывает эти два мира.

Практический вывод: сравнивая два AI-продукта, мы далеко не всегда сравниваем две модели. Один и тот же GPT или Claude показывает совершенно разный результат в зависимости от того, как система выбирает контекст, какие инструменты предоставляет, умеет ли запускать проверки, хранить состояние, делать retry и контролировать результат.

Значительная часть воспринимаемой "умности" AI-продукта находится уже не внутри модели, а вокруг нее. Отсюда термин harness engineering: по мере сближения возможностей сильных моделей качество определяется средой их работы. Для enterprise AI вопрос смещается от "какую модель взять?" к "как построить вокруг модели надежную систему исполнения?".

## Архитектура: control plane и execution plane

Harness удобно рассматривать как control plane AI-агента, отделенный от среды исполнения. Модель принимает решения, но сама не работает напрямую с файловой системой, БД, shell или корпоративными API. Между моделью и внешней средой — harness: интерпретирует решение, выбирает допустимый инструмент, проверяет параметры и права, выполняет действие, возвращает фактический результат в контекст.

```
Task → State → Context → Model → Decision → Tool → Environment → Result → State
```

Цикл повторяется до условия завершения.

**Control plane** (ход процесса): состояние задачи, контекст, выбор модели, доступные tools, permissions, retries, approvals, лимиты, orchestration, критерии завершения.

**Execution plane** (действия): shell-команды, БД и API, файлы, Git, браузер, корпоративные приложения. Часто изолируется sandbox.

Разделение критично для безопасности: решение модели вероятностно, а изменение прод-системы — детерминированный side effect. Между ними контролируемый контракт: модель не "работает с ERP вообще", а получает tool create_order(parameters) с определенной схемой, разрешениями и известной семантикой.

## Состояние, идемпотентность, контекст

Долгоживущий агент требует полноценной модели состояния (state machine):

```
NEW → ANALYZING → WAITING_FOR_TOOL → ANALYZING → WAITING_FOR_APPROVAL → EXECUTING → VERIFYING → DONE
```

плюс FAILED, RETRYING, TIMEOUT, CANCELLED. Важно для UI и для восстановления: какие действия выполнены, какие безопасно повторить, какие требуют компенсации.

Отсюда классическая проблема idempotency: вызов create_order() с timeout — неизвестно, создан ли заказ; повтор может дать дубль. Agentic systems наследуют проблемы распределенных систем: at-least-once execution, partial failure, retry policy, correlation IDs, deduplication, recovery.

Context manager — отдельный компонент: state системы и context модели не одно и то же. Полное состояние хранится вовне, в каждый model call передается только релевантная проекция большого состояния в ограниченное context window.

При нескольких агентах добавляется orchestration: кто получает подзадачу, какой контекст передается, какие результаты общие, кто принимает итоговое решение.

Итог: production AI-agent — не "LLM с функциями", а обычная распределенная информационная система с вероятностным механизмом принятия решений внутри. Ключевой вопрос проектировщика — где заканчивается свобода модели и начинается детерминированный контур. Чем яснее граница, тем надежнее, безопаснее и предсказуемее агент.

## Маппинг на нашу практику

| У Бескова | У нас |
|-----------|-------|
| human approval, approvals на high-risk | per-risk-tier gate: survivor → Open finding с записанным решением; zero-tolerance B0/B1 |
| evaluators (проверка, выполнена ли задача) | decision validation (слой QBurst L2: right tool, right params, right order) + mutation matrix как независимый оракул |
| permissions, sandbox, контракт tool | execution plane isolation; least privilege per tool |
| state machine, idempotency, at-least-once | требования к evidence packs: какие шаги выполнены/повторены; no-op rule (невидимый survivor — дефект сидера) |
| context manager (проекция state → context) | append-only шины (чекпоинт, log): полное состояние вовне, в окно — релевантный хвост |
| harness engineering как дисциплина | курс walkinglabs (пять подсистем) + Pi/OpenCode-интеграция как живой харнес |
