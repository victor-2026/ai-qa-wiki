## Go‑тестирование для QA‑инженеров  

**Дата:** 28 июня 2026 г.  
**Контекст:** подготовка к роли Test Lead в Avito, где Go‑код является основной частью бек‑энда.

---

### 📋 Краткое содержание  
Avito активно использует Go, поэтому QA‑lead обязан разбираться в его тестовой экосистеме: писать и оценивать unit‑ и интеграционные тесты, проводить code‑review и поддерживать покрытие. В статье собраны базовые приёмы Go‑тестирования, популярные библиотеки и рекомендации, принятые в компании.

## 🔑 Ключевые понятия  

| Понятие | Что это | Почему важно для QA |
|--------|----------|--------------------|
| **`testing`‑пакет** | Стандартный набор функций (`TestXxx`, `t.Errorf`, `t.Run`). | Позволяет запускать тесты командой `go test ./...`. |
| **Table‑driven tests** | Описание наборов входных данных в виде среза структур и их перебор в цикле. | Идиоматический стиль Go, облегчает добавление новых кейсов и читаемость. |
| **Subtests (`t.Run`)** | Вложенные тесты, каждый с собственным именем. | Делает возможным выборочный запуск (`-run TestAdd/positive`) и параллелизм (`t.Parallel`). |
| **`httptest`** | Встроенный сервер‑мок для HTTP‑обработчиков. | Позволяет проверять API без развёртывания реального сервиса, удобно для контрактных проверок. |
| **`testify`** | Библиотека с удобными ассертами и возможностью группировать тесты в «suite». | Уменьшает количество boilerplate‑кода и делает сообщения об ошибках более информативными. |
| **Pact‑go** | Инструмент для contract‑testing (потребитель‑провайдер). | Критичен для согласования API между разными командами Avito. |
| **Coverage** | Метрика покрытого кода (`go test -cover`). | Avito требует 50‑80 % покрытие; помогает контролировать качество тестов. |
| **Fuzzing** | Генерация случайных входов (`testing/f`). | Позволяет находить краевые случаи, особенно после Go 1.18. |

## 🚀 Практические применения  

1. **Unit‑тесты бизнес‑логики** – пишем функции в виде table‑driven тестов, проверяем корректность расчётов, валидаций и т.п.  
2. **API‑тесты без инфраструктуры** – с помощью `httptest.NewServer` создаём лёгкий мок‑сервер, отправляем запросы и проверяем ответы (статусы, JSON‑поле).  
3. **Ассерты и наборы тестов** – `testify/assert` заменяет ручные `if`‑проверки, а `testify/suite` позволяет инициализировать общие ресурсы (БД, кеш) в `SetupTest`.  
4. **Контрактные тесты** – описываем ожидаемые запросы/ответы в Pact‑scenario, генерируем мок‑сервер и проверяем, что провайдер удовлетворяет договору.  
5. **CI‑оптимизация** – используем `t.Parallel()` в subtests, а также `go test -run` для избирательного запуска, что ускоряет пайплайн.  
6. **Отчётность** – генерируем coverage‑файл и визуализируем его (`go tool cover -html`), следим за трендами в дашбордах.

## 🔗 Связанные темы  

- **Go modules** – управление зависимостями (`go.mod`, `go.sum`).  
- **Mock‑генераторы** (например, `gomock`, `mockery`) – для изоляции внешних сервисов.  
- **CI/CD** – интеграция тестов в GitLab CI, GitHub Actions, использование `go test -json` для парсинга результатов.  
- **Performance testing** – пакет `testing/benchmark` и инструменты вроде `pprof`.  
- **Static analysis** – `golint`, `go vet`, `staticcheck` для раннего обнаружения проблем в тестах.
